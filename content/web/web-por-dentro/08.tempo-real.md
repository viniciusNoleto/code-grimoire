Há várias formas de o servidor falar com a página sem que ela pergunte a cada vez. Elas diferem na direção, no transporte e em quem cuida da reconexão.

|  | Polling | Long polling | SSE | WebSocket | WebTransport | WebRTC |
| --- | --- | --- | --- | --- | --- | --- |
| Direção | cliente pergunta | cliente pergunta, servidor segura | servidor → cliente | bidirecional | bidirecional | par a par |
| Transporte | HTTP | HTTP | HTTP | TCP (upgrade) | HTTP/3 (QUIC) | UDP (SRTP, SCTP) |
| Dados | qualquer | qualquer | texto | texto e binário | streams e datagramas | áudio, vídeo, dados |
| Reconexão | implícita | implícita | automática, com retomada | manual | manual | ICE restart |
| Bom para | raramente muda | legado | feeds, notificações, progresso, LLMs | chat, jogos, colaboração | jogos, mídia de baixa latência | chamadas, compartilhamento de tela |

### Server-Sent Events

SSE é uma resposta HTTP comum, com `Content-Type: text/event-stream`, que nunca termina. O servidor escreve blocos de texto terminados por linha em branco, com os campos `data`, `event`, `id` e `retry`. O `EventSource` do navegador faz o parsing, reconecta sozinho e envia `Last-Event-ID` para o servidor retomar de onde parou.

::workbench{demo="sse-simulator" title="Simulador de stream"}
Um servidor falso escreve no fio e um parser seguindo as regras do EventSource monta os eventos. Derrube a conexão para ver a reconexão com `Last-Event-ID`.
::

```js [sse.js]
const es = new EventSource('/stream', { withCredentials: true });
es.addEventListener('preco', (e) => atualizar(JSON.parse(e.data), e.lastEventId));
es.onmessage = (e) => { /* eventos sem campo "event" */ };
es.onerror = () => { if (es.readyState === EventSource.CLOSED) avisarQueCaiu(); };
// es.close() para encerrar. Limitações: sem headers customizados, só GET, só texto,
// ~6 conexões por domínio em HTTP/1.1 (sem limite prático em HTTP/2).
```

### WebSocket

Começa como uma requisição HTTP com `Upgrade: websocket`; o servidor responde `101 Switching Protocols` e a conexão TCP vira um canal de *frames* nos dois sentidos. Não tem reconexão, retomada nem confirmação de entrega: isso é responsabilidade sua (ou de bibliotecas como Socket.IO).

```js [websocket.js]
function conectar(tentativa = 0) {
  const ws = new WebSocket('wss://api.loja.com/ws');
  ws.binaryType = 'arraybuffer';

  ws.onopen = () => { tentativa = 0; ws.send(JSON.stringify({ tipo: 'assinar', canal: 'pedidos' })); };
  ws.onmessage = (e) => tratar(JSON.parse(e.data));
  ws.onclose = (e) => {
    if (e.code === 1000) return;                                    // fechamento normal
    const espera = Math.min(30000, 1000 * 2 ** tentativa) * (0.5 + Math.random()); // backoff com jitter
    setTimeout(() => conectar(tentativa + 1), espera);
  };
  return ws;
}
// Backpressure: confira ws.bufferedAmount antes de enviar muito. Autenticação: token na
// primeira mensagem ou cookie (o handshake não aceita headers customizados no navegador).
// WebSocketStream (Chromium) oferece uma API com streams e backpressure nativo.
```

### WebTransport e WebRTC

- **WebTransport** roda sobre HTTP/3 e oferece vários streams independentes (sem head-of-line blocking) e **datagramas** não confiáveis, ideais quando um pacote atrasado já não serve (posição num jogo).
- **WebRTC** conecta navegadores diretamente. Precisa de um servidor de *sinalização* (qualquer canal: WebSocket, HTTP) para trocar ofertas SDP e candidatos ICE, de servidores **STUN** para descobrir o IP público e de **TURN** para retransmitir quando a conexão direta é impossível. Além de áudio e vídeo, `RTCDataChannel` transmite dados arbitrários com baixa latência.
