Deploy de Laravel é previsível quando segue sempre os mesmos passos e quando as migrations e workers são tratados com cuidado.

### Servidor

- PHP 8.2+ (Laravel 11 e 12) ou 8.3+ (Laravel 13), com as extensões `ctype`, `curl`, `dom`, `fileinfo`, `mbstring`, `openssl`, `pdo`, `tokenizer`, `xml`, e o driver do banco.
- O servidor web aponta para `public/`, nunca para a raiz do projeto.
- `storage/` e `bootstrap/cache/` precisam ser graváveis pelo usuário do PHP.

```nginx
server {
    root /var/www/loja/current/public;
    index index.php;
    location / { try_files $uri $uri/ /index.php?$query_string; }
    location ~ \.php$ {
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
        include fastcgi_params;
    }
    location ~ /\.(?!well-known) { deny all; }
}
```

### Passo a passo de um deploy

```bash
git fetch && git checkout <tag-da-versao>          # ou: nova pasta de release
composer install --no-dev --optimize-autoloader --no-interaction
npm ci && npm run build
php artisan migrate --force
php artisan optimize
php artisan queue:restart                          # ou horizon:terminate
sudo systemctl reload php8.3-fpm                   # limpa o OPcache
```

`php artisan storage:link` só na primeira vez. Se usar Octane: `php artisan octane:reload`.

### Zero downtime

Ferramentas como Forge, Envoyer, Deployer e o Laravel Cloud fazem deploy em pastas de release separadas e trocam um symlink (`current`) no fim, então os usuários nunca veem a aplicação pela metade. Para isso funcionar:

- `storage/` e `.env` ficam numa pasta compartilhada entre releases.
- Migrations precisam ser compatíveis com o código **anterior** e o **novo** ao mesmo tempo: primeiro adicione colunas, depois passe a usá-las, e só num deploy seguinte remova o que ficou sem uso.

### Workers e agendador

```ini
; /etc/supervisor/conf.d/loja-worker.conf
[program:loja-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/loja/current/artisan queue:work redis --queue=alta,default --sleep=3 --tries=3 --max-time=3600
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
user=www-data
numprocs=4
stopwaitsecs=3600          ; maior que o job mais longo
redirect_stderr=true
stdout_logfile=/var/www/loja/shared/storage/logs/worker.log
```

Com Horizon, um único programa no Supervisor roda `php artisan horizon`, e o Horizon gerencia os processos. O agendador precisa da linha no cron ([seção 41.1](#agendamento-configuração-no-servidor)).

### Variáveis de produção

| Variável | Valor |
| --- | --- |
| `APP_ENV` | `production` |
| `APP_DEBUG` | `false` |
| `APP_KEY` | Gerada uma vez (`php artisan key:generate`) e nunca trocada sem `APP_PREVIOUS_KEYS` |
| `APP_URL` | URL pública com `https` |
| `LOG_CHANNEL`, `LOG_LEVEL` | `daily` ou `stderr`; `warning` ou `error` |
| `CACHE_STORE`, `SESSION_DRIVER`, `QUEUE_CONNECTION` | `redis` (ou `database`) |
| `SESSION_SECURE_COOKIE` | `true` |

### Observabilidade e manutenção

- **Health check**: a rota `/up` (Laravel 11+) responde 200 se a aplicação inicializa; use no balanceador e no monitor de uptime.
- **Modo de manutenção** durante migrations longas: `php artisan down --secret=...` ([seção 5.5](#instalacao-e-configuracao-modo-de-manutenção)).
- **Monitoramento**: Pulse ou Nightwatch, rastreamento de erros (Sentry, Flare), alertas de fila (`queue:monitor`) e de cron (`pingOnSuccess`).
- **Backups**: banco e arquivos, com teste de restauração. O pacote `spatie/laravel-backup` automatiza.

### Onde hospedar

| Opção | Perfil |
| --- | --- |
| Laravel Cloud | Plataforma oficial gerenciada: deploy por Git, banco, cache, filas e escala automática |
| Forge | Provisiona e gerencia seus próprios servidores (AWS, DigitalOcean, Hetzner…) |
| Vapor | Serverless na AWS Lambda |
| Docker/Kubernetes | Controle total; imagens com PHP-FPM + Nginx ou FrankenPHP |
| Hospedagem compartilhada | Possível, mas sem workers de fila contínuos e com limitações |
