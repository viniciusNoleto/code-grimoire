Toda requisição HTTP entra por um único arquivo, `public/index.php`, passa pelo container, pelos middlewares e pela rota, e volta pelo mesmo caminho como resposta. Entender esse trajeto explica onde cada peça do Laravel atua.

### O caminho completo

1. O servidor web (Nginx, Apache) envia toda requisição para `public/index.php`.
2. O `index.php` verifica o modo de manutenção, carrega o autoload do Composer e cria a aplicação a partir de `bootstrap/app.php`.
3. A aplicação (que é o **Service Container**) carrega `.env`, configuração, tratamento de erros e facades, e então **registra** e depois **inicializa** (boot) todos os Service Providers.
4. A requisição atravessa os **middlewares globais** (proxies confiáveis, CORS, tamanho do POST, trim de strings…).
5. O **Router** encontra a rota, aplica os middlewares do grupo (`web` ou `api`) e os da própria rota.
6. O controller (ou closure) é resolvido pelo container, com as dependências injetadas, e devolve uma resposta.
7. A resposta volta pelos middlewares em ordem inversa, é enviada ao cliente e, por fim, roda o `terminate()` dos middlewares e as tarefas adiadas com `defer()`.

```php
// public/index.php (Laravel 11+)
define('LARAVEL_START', microtime(true));

if (file_exists($maintenance = __DIR__.'/../storage/framework/maintenance.php')) {
    require $maintenance;                       // modo de manutenção
}

require __DIR__.'/../vendor/autoload.php';      // autoload do Composer

(require_once __DIR__.'/../bootstrap/app.php')
    ->handleRequest(Request::capture());        // container + kernel HTTP
```

### `bootstrap/app.php`: a configuração central

:version[Laravel 11+] Rotas, middlewares e tratamento de exceções são configurados num único arquivo. Versões antigas usavam `app/Http/Kernel.php` e `app/Exceptions/Handler.php`, que deixaram de existir.

```php
use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Exceptions;
use Illuminate\Foundation\Configuration\Middleware;

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        api: __DIR__.'/../routes/api.php',        // criado por php artisan install:api
        commands: __DIR__.'/../routes/console.php',
        health: '/up',                            // rota de health check
    )
    ->withMiddleware(function (Middleware $middleware): void {
        $middleware->alias(['admin' => EnsureUserIsAdmin::class]);
    })
    ->withExceptions(function (Exceptions $exceptions): void {
        // relatório e renderização de exceções (seção 48)
    })
    ->create();
```

### Os pontos de entrada

A mesma aplicação é iniciada por caminhos diferentes, e cada um tem o seu "kernel":

| Entrada | Quem inicia | Onde você configura |
| --- | --- | --- |
| Requisição HTTP | `public/index.php` | `routes/web.php`, `routes/api.php`, middlewares |
| Comando Artisan | `artisan` | `routes/console.php`, `app/Console/Commands` |
| Job de fila | `php artisan queue:work` | classes em `app/Jobs`, listeners na fila |
| Agendamento | `php artisan schedule:run` (cron) | `routes/console.php` com `Schedule::` |
| Octane | servidor Octane, app fica em memória | `config/octane.php` ([seção 52.6](#performance-octane)) |

::note{type="pitfall" title="Atenção"}
No Octane e nos workers de fila a aplicação **não morre** entre uma requisição (ou job) e outra. Dados guardados em propriedades estáticas ou singletons vazam para a próxima execução.
::

### Register, boot e por que a ordem importa

Os providers rodam em duas etapas. Primeiro o `register()` de **todos** eles, depois o `boot()` de todos. No `register()` você só registra bindings no container; no `boot()` pode usar qualquer serviço, porque todos já foram registrados (detalhes na [seção 3](#service-providers)).

### Depois da resposta: `terminate` e `defer`

Um middleware com método `terminate($request, $response)` roda depois que a resposta foi enviada. O helper `defer()` (*Laravel 11+*) faz o mesmo para qualquer trecho de código, sem fila:

```php
Route::post('/pedidos', function (Request $request) {
    $pedido = Pedido::create($request->validated());

    defer(fn () => Metricas::registrar('pedido_criado', $pedido->id));  // roda após enviar a resposta

    return response()->json($pedido, 201);
});
```

::note{type="tip" title="Regra prática"}
Trabalho curto que não pode atrasar a resposta vai em `defer()`; trabalho longo, que precisa de novas tentativas ou que pode falhar, vai para uma fila ([seção 39](#filas-e-jobs)).
::
