Um projeto Laravel é configurado por arquivos em `config/`, que leem valores do `.env`. Saber como essas duas camadas se relacionam evita os bugs mais comuns de produção.

### Criar um projeto

```bash
laravel new loja                    # instalador oficial: pergunta starter kit, testes e banco
composer create-project laravel/laravel loja   # alternativa sem o instalador
php artisan serve                   # servidor de desenvolvimento em http://localhost:8000
```

Para ambiente local, as opções oficiais são o **Herd** (macOS e Windows, PHP e Nginx nativos) e o **Sail** (Docker). O Laravel 11 e o 12 exigem PHP 8.2+; o Laravel 13 exige PHP 8.3+.

### `.env` e `config/`

O `.env` guarda valores que mudam por ambiente e segredos; nunca vai para o Git. Os arquivos de `config/` leem esses valores com `env()` e definem padrões.

```ini [.env]
PAGAMENTO_KEY=sk_live_123
PAGAMENTO_TIMEOUT=15
```

```php [config/services.php]
return [
    // ...
    'pagamento' => [
        'key' => env('PAGAMENTO_KEY'),
        'timeout' => env('PAGAMENTO_TIMEOUT', 10),   // segundo argumento: valor padrão
    ],
];
```

```php [app/Services/GatewayPagamento.php]
$chave = config('services.pagamento.key');
config(['services.pagamento.timeout' => 30]);    // altera em tempo de execução (só nesta requisição)
```

::note{type="pitfall" title="Cuidado"}
Chame `env()` **apenas** dentro de `config/`. Depois de `php artisan config:cache` (feito em todo deploy), o `.env` não é mais lido e `env()` fora de `config/` devolve `null`.
::

Comandos para inspecionar e manter a configuração:

```bash
php artisan config:show database
```

Mostra a configuração **final** de um arquivo de `config/`, já com os valores do `.env` aplicados e os padrões preenchidos. É o jeito de responder "qual valor a aplicação está usando de verdade?" sem abrir o `.env` e o arquivo de config e cruzar os dois na cabeça. Aceita um arquivo inteiro (`database`) ou uma chave (`database.connections.pgsql`).

```bash
php artisan config:publish cors
php artisan config:publish --all
```

:version[Laravel 11+] A partir do Laravel 11, vários arquivos de configuração (`cors.php`, `broadcasting.php`, `hashing.php`, `view.php`…) não vêm mais no projeto novo: o framework usa os padrões internos. Quando você precisa mudar algum deles, este comando copia o arquivo padrão para `config/` e, daí em diante, a sua cópia vale. `--all` publica todos.

```bash
php artisan env:encrypt                      # gera .env.encrypted e mostra a chave
php artisan env:encrypt --env=production     # criptografa .env.production
php artisan env:decrypt --key=base64:...     # recria o .env a partir do .env.encrypted
```

O `.env` não vai para o Git porque tem segredos. O `env:encrypt` gera um `.env.encrypted`, que **pode** ser versionado: sem a chave ele é ilegível. No deploy, o servidor recebe só a chave (numa variável `LARAVEL_ENV_ENCRYPTION_KEY`) e roda `env:decrypt` para recriar o `.env`. Assim os segredos ficam no repositório, com histórico, sem estarem expostos.

```bash
php artisan config:cache     # junta toda a config/ num arquivo só, em bootstrap/cache/config.php
php artisan config:clear     # apaga esse arquivo; a config volta a ser lida a cada requisição
```

`config:cache` é feito em todo deploy de produção: em vez de ler dezenas de arquivos e o `.env` a cada requisição, o Laravel carrega um único array já pronto. Em desenvolvimento não use: qualquer mudança no `.env` só valeria depois de rodar o comando de novo.

### Ambiente

```php [app/Providers/AppServiceProvider.php]
app()->environment();                        // 'local', 'production'…
app()->environment(['local', 'staging']);    // true se for um deles
app()->isProduction();
app()->isLocal();
```

`APP_ENV` define o ambiente e `APP_DEBUG` liga as páginas de erro detalhadas. Nunca deixe `APP_DEBUG=true` em produção: a página de erro mostra variáveis de ambiente e trechos de código.

### Estrutura de diretórios (Laravel 11+)

| Pasta | Conteúdo |
| --- | --- |
| `app/Http/Controllers` | Controllers |
| `app/Models` | Models Eloquent |
| `app/Providers` | Service Providers (por padrão, só o `AppServiceProvider`) |
| `bootstrap/app.php` | Rotas, middlewares e exceções |
| `bootstrap/providers.php` | Lista de providers |
| `config/` | Configuração |
| `database/` | Migrations, factories, seeders |
| `public/` | Único diretório exposto pelo servidor web: `index.php` e assets compilados |
| `resources/` | Views Blade, CSS e JS de origem, traduções |
| `routes/` | `web.php`, `console.php`; `api.php` e `channels.php` quando instalados |
| `storage/` | Logs, cache de framework, sessões e arquivos enviados |
| `tests/` | `Feature` e `Unit` |

Pastas como `app/Jobs`, `app/Events`, `app/Policies` e `app/Http/Middleware` só aparecem quando você cria o primeiro arquivo com `php artisan make:*`.

### Modo de manutenção

Com a aplicação em manutenção, toda requisição recebe uma resposta **503 Service Unavailable** em vez de rodar a aplicação. Usado durante deploys com migrations demoradas ou intervenções no servidor.

```bash
php artisan down
php artisan up
```

`down` cria o arquivo `storage/framework/down`; enquanto ele existir, o middleware `PreventRequestsDuringMaintenance` barra as requisições. `up` apaga o arquivo e a aplicação volta.

```bash
php artisan down --secret="acesso-equipe"
```

Gera uma rota de bypass: quem acessar `https://loja.com/acesso-equipe` recebe um cookie e navega normalmente enquanto o resto do público vê a página de manutenção. Serve para a equipe testar o deploy em produção antes de liberar.

```bash
php artisan down --render="errors::503"
```

O `--render` define **qual view Blade** será exibida, e ela é renderizada **no momento do `down`**, não a cada requisição. O HTML resultante fica guardado em `storage/framework/down` e é devolvido direto, sem carregar o framework nem tocar banco, cache ou sessão (que podem estar fora do ar justamente por causa da manutenção). O valor segue a notação de views: `errors::503` é a view `503` do namespace `errors`, ou seja, `resources/views/errors/503.blade.php` se você a criou, ou a página padrão do Laravel se não.

```html [resources/views/errors/503.blade.php]
<h1>Voltamos em instantes</h1>
<p>Estamos atualizando a loja. Tente novamente em alguns minutos.</p>
```

Como o HTML é gerado uma vez, a view não pode depender de dados dinâmicos da requisição (usuário logado, carrinho). Se você editar o arquivo da view, rode `down --render` de novo para gerar o HTML atualizado.

```bash
php artisan down --retry=60          # cabeçalho Retry-After: 60 na resposta 503
php artisan down --refresh=15        # a página se recarrega sozinha a cada 15 segundos
php artisan down --redirect=/        # redireciona toda requisição para / em vez de mostrar a página
```

`--retry` informa a navegadores e robôs de busca quando tentar de novo (evita que o Google trate o 503 como site fora do ar). `--refresh` é útil para o usuário que deixou a aba aberta: quando a manutenção acabar, a página volta sozinha. As opções combinam entre si:

```bash
php artisan down --secret="acesso-equipe" --render="errors::503" --retry=60 --refresh=15
```
