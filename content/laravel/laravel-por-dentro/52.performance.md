A maior parte dos problemas de desempenho em Laravel vem do banco (N+1, falta de índice, colunas demais) e de trabalho síncrono que deveria estar na fila. Ajustes de framework vêm depois.

### Caches do framework em produção

```bash
php artisan optimize          # config:cache + route:cache + view:cache + event:cache
php artisan optimize:clear    # limpa todos
```

| Cache | Efeito | Cuidado |
| --- | --- | --- |
| `config:cache` | Junta `config/` num arquivo | `env()` fora de `config/` passa a devolver `null` |
| `route:cache` | Compila as rotas | Rotas com closure não podem ser cacheadas |
| `view:cache` | Pré-compila o Blade | Rode após cada deploy |
| `event:cache` | Lista listeners sem varrer pastas | Rode após cada deploy |

### PHP e Composer

```bash
composer install --no-dev --optimize-autoloader     # classmap otimizado, sem pacotes de dev
```

Ative o **OPcache** (com `opcache.validate_timestamps=0` em produção, reiniciando o PHP-FPM a cada deploy). Ele guarda o bytecode compilado e é o ganho mais barato de todos.

### Banco de dados

| Problema | Solução |
| --- | --- |
| N+1 queries | `with()`, `withCount()`, `preventLazyLoading()` ([seção 28](#eager-loading-with)) |
| Busca lenta em coluna filtrada | Índice; confira com `->explain()` ou `EXPLAIN ANALYZE` |
| `select *` com colunas grandes (texto, JSON) | `select()` só do necessário |
| `$user->pedidos->count()` | `$user->pedidos()->count()` ou `withCount` |
| Paginação lenta em páginas altas | `cursorPaginate()` |
| Processar milhares de linhas | `chunkById()`, `lazy()`, `cursor()` |
| Muitos `update` em loop | `upsert()` ou update em massa |
| Contagens repetidas | Coluna contadora atualizada por evento, ou cache |
| Leitura muito maior que escrita | Réplicas de leitura ([seção 14.1](#db-transacoes-e-seeders-conexões)) |

### Trabalho fora da requisição

- E-mails, notificações, integrações, PDFs, importações: fila.
- Métricas e logs de terceiros: `defer()`.
- Consultas independentes: `Concurrency::run`; chamadas HTTP independentes: `Http::pool`.

### Cache de aplicação

Cacheie resultados caros com `Cache::remember`/`flexible` ([seção 44](#cache-e-locks)). Use Redis para cache, sessão e filas quando o tráfego crescer, e cabeçalhos de cache HTTP ou CDN para respostas públicas.

### Octane

O Octane mantém a aplicação carregada na memória e atende muitas requisições com o mesmo processo, usando FrankenPHP, Swoole ou RoadRunner. O boot do framework deixa de acontecer a cada requisição.

```bash
composer require laravel/octane
php artisan octane:install --server=frankenphp
php artisan octane:start --workers=8 --max-requests=500
php artisan octane:reload      # após deploy
```

::note{type="pitfall" title="Cuidado"}
S, porque o estado sobrevive entre requisições:
::

- Não guarde dados da requisição em propriedades estáticas ou em singletons. Use `scoped()` no container.
- Não injete `Request`, `config` ou o container no construtor de um singleton; resolva quando precisar.
- `--max-requests` reinicia workers periodicamente, contendo vazamentos de memória.

### Medir antes de otimizar

| Ferramenta | Onde | O que mostra |
| --- | --- | --- |
| Laravel Debugbar | Desenvolvimento | Queries, tempo, memória por página |
| Telescope | Desenvolvimento/homologação | Requisições, queries, jobs, cache, exceções |
| Pulse | Produção | Rotas e queries lentas, jobs, uso por usuário, servidores |
| Nightwatch | Produção | Monitoramento completo (serviço pago) |
| `DB::whenQueryingForLongerThan` | Produção | Alerta de requisições com banco lento |
