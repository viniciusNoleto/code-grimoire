Além do Eloquent, a fachada `DB` dá acesso direto às conexões, ao Query Builder sem Models e às transações.

### Conexões

Uma **conexão** é o conjunto de dados para falar com um banco: driver (pgsql, mysql, sqlite…), host, porta, banco, usuário e senha. Todas ficam declaradas em `config/database.php`, no array `connections`, cada uma com um nome. A variável `DB_CONNECTION` do `.env` escolhe qual é a **padrão**, usada por todo Model e toda chamada `DB::` que não diga outra coisa.

```php [config/database.php]
return [
    'default' => env('DB_CONNECTION', 'pgsql'),

    'connections' => [
        'pgsql' => [
            'driver' => 'pgsql',
            'host' => env('DB_HOST', '127.0.0.1'),
            'port' => env('DB_PORT', '5432'),
            'database' => env('DB_DATABASE', 'loja'),
            'username' => env('DB_USERNAME', 'root'),
            'password' => env('DB_PASSWORD', ''),
        ],

        // segunda conexão: o banco de BI, só leitura
        'relatorios' => [
            'driver' => 'pgsql',
            'host' => env('RELATORIOS_DB_HOST'),
            'database' => env('RELATORIOS_DB_DATABASE'),
            'username' => env('RELATORIOS_DB_USERNAME'),
            'password' => env('RELATORIOS_DB_PASSWORD'),
        ],
    ],
];
```

Casos de uso para mais de uma conexão: um banco de relatórios separado, um sistema legado que a aplicação precisa ler, um banco por cliente (multi-tenant). Para usar uma conexão que não é a padrão:

```php [app/Services/RelatorioService.php]
DB::connection('relatorios')->table('vendas')->sum('valor');          // Query Builder
DB::connection('relatorios')->select('select * from vendas_mensais'); // SQL cru
Venda::on('relatorios')->where('ano', 2026)->get();                   // um Model, só nesta consulta
```

```php [app/Models/Venda.php]
class Venda extends Model
{
    protected $connection = 'relatorios';   // o Model inteiro sempre usa esta conexão
}
```

#### Réplicas de leitura

Em bancos com réplica, o servidor principal recebe as escritas e copia os dados para uma ou mais réplicas, que atendem leituras. O Laravel divide isso sozinho dentro de **uma mesma conexão**: `SELECT` vai para um host de `read`, `INSERT`/`UPDATE`/`DELETE` vão para `write`. As chaves que não estão em `read`/`write` valem para os dois.

```php [config/database.php]
return [
    'connections' => [
        'pgsql' => [
            'driver' => 'pgsql',
            'read'  => ['host' => ['10.0.0.2', '10.0.0.3']],   // sorteia uma réplica por requisição
            'write' => ['host' => ['10.0.0.1']],
            'sticky' => true,
            'database' => env('DB_DATABASE'),
            'username' => env('DB_USERNAME'),
            'password' => env('DB_PASSWORD'),
        ],
    ],
];
```

A réplica recebe as mudanças com um pequeno atraso. Sem `sticky`, um usuário que acabou de salvar um pedido e é redirecionado para a lista pode não ver o pedido novo, porque a leitura caiu numa réplica atrasada. Com `sticky => true`, depois de qualquer escrita na requisição, as leituras seguintes **daquela requisição** vão para o `write`. Para forçar o principal numa consulta específica: `User::useWritePdo()->find($id)`.

### SQL cru

```php [app/Services/RelatorioService.php]
$linhas = DB::select('select * from pedidos where status = ? and total > ?', ['pago', 100]);
$linhas = DB::select('select * from pedidos where status = :status', ['status' => 'pago']);
$um     = DB::selectOne('select count(*) as total from pedidos');
$valor  = DB::scalar('select max(total) from pedidos');

DB::insert('insert into logs (acao) values (?)', ['login']);
$afetadas = DB::update('update pedidos set status = ? where id = ?', ['pago', 10]);
DB::delete('delete from sessoes where last_activity < ?', [$limite]);
DB::statement('refresh materialized view vendas_mensais');
```

`DB::select` devolve um array de objetos `stdClass`, sem casts, eventos ou relacionamentos.

### Query Builder sem Model

```php [app/Services/RelatorioService.php]
DB::table('pedidos')
    ->join('clientes', 'clientes.id', '=', 'pedidos.cliente_id')
    ->where('pedidos.status', 'pago')
    ->select('clientes.nome', DB::raw('sum(pedidos.total) as gasto'))
    ->groupBy('clientes.nome')
    ->orderByDesc('gasto')
    ->get();      // Collection de stdClass
```

Todos os métodos das [seções 18](#filtros-where) a 20 funcionam aqui. Use `DB::table` para relatórios, tabelas sem Model e operações em massa onde eventos não importam.

### Transações

Uma transação agrupa várias operações para que valham **todas ou nenhuma**. Se o pedido é criado, mas a baixa no estoque falha, a transação desfaz a criação do pedido, e o banco nunca fica num estado pela metade. Há três operações no SQL: `BEGIN` abre a transação, `COMMIT` confirma tudo, `ROLLBACK` descarta tudo.

#### Forma 1: `DB::transaction()` com closure (a recomendada)

O Laravel abre a transação, roda a closure e decide sozinho: se a closure termina normalmente, faz `COMMIT`; se ela lança qualquer exceção, faz `ROLLBACK` e relança a exceção. O valor retornado pela closure é o retorno de `DB::transaction()`.

```php [app/Actions/CriarPedido.php]
namespace App\Actions;

use Illuminate\Support\Facades\DB;

class CriarPedido
{
    public function executar(User $cliente, array $dados): Pedido
    {
        return DB::transaction(function () use ($cliente, $dados) {
            $pedido = $cliente->pedidos()->create($dados);          // INSERT pedidos
            $pedido->itens()->createMany($dados['itens']);          // INSERT itens
            Estoque::baixar($dados['itens']);                       // UPDATE estoque; lança se faltar
            return $pedido;
        });
        // BEGIN … COMMIT se tudo deu certo; BEGIN … ROLLBACK se algo lançou exceção
    }
}
```

```php [app/Actions/TransferirSaldo.php]
// attempts: em deadlock (dois processos esperando um pelo outro), roda a closure de novo
DB::transaction(function () use ($origem, $destino, $valor) {
    $origem->decrement('saldo', $valor);
    $destino->increment('saldo', $valor);
}, attempts: 3);
```

::note{type="pitfall" title="Não engula a exceção"}
Se você colocar um `try/catch` **dentro** da closure e não relançar, o Laravel não vê o erro e faz `COMMIT` do que já foi executado. O rollback só acontece quando a exceção sai da closure.
::

#### Forma 2: controle manual

Útil quando a transação não cabe numa closure: começa num método e termina em outro, ou você precisa decidir o rollback por uma condição que não é exceção.

```php [app/Services/ImportadorDeNotas.php]
DB::beginTransaction();                // BEGIN

try {
    $nota = NotaFiscal::create($dados);
    $resultado = $this->sefaz->autorizar($nota);

    if (! $resultado->autorizada) {
        DB::rollBack();                // ROLLBACK por regra de negócio, sem exceção
        return null;
    }

    $nota->update(['chave' => $resultado->chave]);
    DB::commit();                      // COMMIT
    return $nota;
} catch (Throwable $e) {
    DB::rollBack();                    // ROLLBACK em qualquer erro
    throw $e;
}
```

Na forma manual, esquecer o `commit()` ou o `rollBack()` num caminho deixa a transação aberta, segurando locks até a conexão fechar. Por isso a closure é preferível.

#### Transações aninhadas (savepoints)

Chamar `DB::transaction()` dentro de outra não abre uma segunda transação: o Laravel cria um **savepoint**, um ponto de retorno dentro da transação externa. Se a interna falhar e a exceção for tratada, só o trabalho dela é desfeito; o `COMMIT` real só acontece quando a mais externa termina.

```php [app/Actions/FecharMes.php]
DB::transaction(function () {
    Fechamento::create([...]);                         // BEGIN

    foreach ($lojas as $loja) {
        try {
            DB::transaction(fn () => $loja->consolidar());   // SAVEPOINT trans2
        } catch (ErroDeConsolidacao $e) {
            report($e);                                // ROLLBACK TO SAVEPOINT trans2: só esta loja
        }
    }
});                                                    // COMMIT
```

`DB::transactionLevel()` diz em que profundidade você está (0 = fora de transação).

#### Outras conexões e efeitos depois do commit

```php [app/Services/RelatorioService.php]
DB::connection('relatorios')->transaction(fn () => /* ... */);   // a transação é por conexão
```

```php [app/Actions/CriarPedido.php]
DB::transaction(function () use ($dados) {
    $pedido = Pedido::create($dados);

    DB::afterCommit(fn () => Cache::forget('vendas-do-dia'));     // roda só se confirmar
    EnviarConfirmacao::dispatch($pedido)->afterCommit();          // job só vai para a fila depois do COMMIT
});
```

::note{type="pitfall" title="Atenção"}
E-mails, jobs e chamadas externas disparados dentro de uma transação podem acontecer mesmo que ela seja desfeita depois. Pior: um job enviado antes do commit pode rodar no worker e não achar o pedido, que ainda não foi confirmado. Use `afterCommit()` nos jobs ([seção 39.8](#filas-e-jobs-filas-e-transações)) e `DB::afterCommit()` para o resto.
::

### Seeders

Seeders são classes que **inserem dados** no banco: dados obrigatórios para a aplicação funcionar (papéis, estados, configurações) e dados falsos para desenvolver e testar. Ficam em `database/seeders/`.

Comandos:

```bash
php artisan make:seeder ProdutoSeeder
```

Cria `database/seeders/ProdutoSeeder.php`, com um método `run()` vazio.

```bash
php artisan db:seed
```

Roda o `DatabaseSeeder`, que é o ponto de entrada: só o que ele chama (direta ou indiretamente) é executado.

```bash
php artisan db:seed --class=ProdutoSeeder
```

Roda apenas um seeder, sem passar pelo `DatabaseSeeder`. Útil para repovoar uma tabela.

```bash
php artisan migrate:fresh --seed
```

Apaga todas as tabelas, roda todas as migrations do zero e depois o `DatabaseSeeder`. É o "recomeçar do zero" do desenvolvimento; nunca em produção.

```bash
php artisan db:seed --force
```

Em produção o Laravel pede confirmação; `--force` pula a pergunta (para scripts de deploy).

O seeder principal:

```php [database/seeders/DatabaseSeeder.php]
namespace Database\Seeders;

use App\Models\Pedido;
use App\Models\User;
use Illuminate\Database\Console\Seeds\WithoutModelEvents;
use Illuminate\Database\Seeder;

class DatabaseSeeder extends Seeder
{
    use WithoutModelEvents;

    public function run(): void
    {
        $this->call([CategoriaSeeder::class, ProdutoSeeder::class]);

        User::factory()->create(['email' => 'admin@loja.test']);

        Pedido::factory()->count(50)->create();
    }
}
```

Linha a linha:

- `use WithoutModelEvents`: durante o seed, eventos de Model não disparam. Observers que enviam e-mail de boas-vindas ou geram notificações a cada `User` criado ficam quietos.
- `$this->call([...])`: roda outros seeders, **na ordem do array**. Categorias antes de produtos, porque produtos precisam de uma categoria existente. Separar em vários seeders permite rodar cada um isolado com `--class`.
- `User::factory()->create([...])`: usa a factory do Model ([seção 33](#factories)) para criar um usuário com dados falsos, sobrescrevendo só o e-mail, para que você saiba como entrar.
- `Pedido::factory()->count(50)->create()`: 50 pedidos com dados aleatórios, para ter volume para testar listagens e paginação.

Um seeder de dados obrigatórios:

```php [database/seeders/CategoriaSeeder.php]
namespace Database\Seeders;

use App\Models\Categoria;
use Illuminate\Database\Seeder;

class CategoriaSeeder extends Seeder
{
    public function run(): void
    {
        foreach (['Livros', 'Filmes', 'Música'] as $nome) {
            Categoria::updateOrCreate(['slug' => str($nome)->slug()], ['nome' => $nome]);
        }
    }
}
```

Seeders de dados obrigatórios (papéis, configurações) devem ser **idempotentes**, ou seja, poder rodar várias vezes com o mesmo resultado: `updateOrCreate` ou `upsert` atualizam o que já existe em vez de duplicar. Assim o mesmo seeder serve no deploy de produção (`db:seed --class=CategoriaSeeder --force`) sem risco.

### Redis

O Redis é um banco de dados **em memória**, de chave e valor, muito rápido (operações em microssegundos). Não substitui o PostgreSQL: os dados ficam na RAM e servem para o que é temporário, compartilhado entre processos ou precisa de velocidade. Ele guarda strings, contadores, listas, conjuntos e hashes, e cada chave pode ter um prazo de expiração.

A conexão é configurada em `config/database.php`, na chave `redis` (`REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`), e o cliente PHP padrão é a extensão `phpredis`.

```php [app/Http/Controllers/ProdutoController.php]
use Illuminate\Support\Facades\Redis;

Redis::set('visitas', 0);                 // grava uma chave
Redis::incr('visitas');                   // soma 1 de forma atômica (sem condição de corrida)
Redis::expire('visitas', 3600);           // a chave some em 1 hora
Redis::get('visitas');                    // "1"
Redis::connection('cache')->get('chave'); // outra conexão Redis (outro banco lógico)
```

Casos de uso diretos: contador de visualizações (o `incr` é atômico, então duas requisições simultâneas nunca perdem um incremento), ranking com conjuntos ordenados (`zadd`/`zrevrange`), presença de usuários online, filas simples.

```php [app/Services/RankingService.php]
Redis::zincrby('ranking:produtos', 1, "produto:$id");        // +1 venda para o produto
Redis::zrevrange('ranking:produtos', 0, 9, 'WITHSCORES');    // top 10
```

Cada comando é uma ida e volta pela rede. Para muitas operações, o **pipeline** junta tudo num envio só:

```php [app/Console/Commands/AquecerCache.php]
Redis::pipeline(function ($pipe) {               // 1000 comandos, uma ida ao servidor
    foreach (range(1, 1000) as $i) {
        $pipe->set("k:$i", $i);
    }
});
```

Na prática, você raramente chama `Redis::` direto: o Redis aparece no Laravel **por baixo** de outros recursos, configurado por variável de ambiente:

| Recurso | Configuração | Seção |
| --- | --- | --- |
| Cache | `CACHE_STORE=redis` | [44](#cache-e-locks) |
| Filas e Horizon | `QUEUE_CONNECTION=redis` | [39](#filas-e-jobs) |
| Sessões | `SESSION_DRIVER=redis` | [9.4](#requests-e-sessao-sessão) |
| Locks atômicos | `Cache::lock()` com store redis | [44](#cache-e-locks) |
| Rate limiting | Usa o store de cache | [6.7](#rotas-rate-limiting-nas-rotas) |

### Monitorar e inspecionar

Há duas frentes: código que **observa as queries** enquanto a aplicação roda, e comandos Artisan para **inspecionar o banco** pelo terminal.

#### Registrar cada query: `DB::listen`

Registra uma função chamada depois de **cada** query executada, recebendo um objeto `QueryExecuted` com o SQL, os bindings, o tempo em milissegundos e a conexão. Fica no `boot()` de um provider.

```php [app/Providers/AppServiceProvider.php]
namespace App\Providers;

use Illuminate\Database\Events\QueryExecuted;
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\Log;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        if ($this->app->isLocal()) {
            DB::listen(function (QueryExecuted $q) {
                Log::debug($q->toRawSql(), ['ms' => $q->time]);   // SQL com os valores no lugar dos ?
            });
        }

        // em produção: só queries lentas
        DB::listen(function (QueryExecuted $q) {
            if ($q->time > 1000) {
                Log::warning('Query lenta', ['sql' => $q->sql, 'ms' => $q->time]);
            }
        });
    }
}
```

Caso de uso: descobrir em desenvolvimento quantas queries uma página faz (problema N+1) ou achar, em produção, a consulta que precisa de índice.

#### Tempo total por requisição: `DB::whenQueryingForLongerThan`

Em vez de olhar uma query isolada, soma o tempo de **todas** as queries da requisição (ou do job) e chama a função uma vez quando o total passa do limite. Pega o caso de cem queries rápidas que, juntas, deixam a página lenta.

```php [app/Providers/AppServiceProvider.php]
use Illuminate\Database\Connection;

class AppServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        DB::whenQueryingForLongerThan(500, function (Connection $conexao, QueryExecuted $evento) {
            Log::warning('Requisição passou de 500ms em queries', [
                'url' => request()->fullUrl(),
                'conexao' => $conexao->getName(),
            ]);
        });
    }
}
```

#### Comandos de inspeção

```bash
php artisan db:show
```

Visão geral da conexão: banco, versão, tamanho total, número de conexões abertas e a lista de tabelas com o tamanho de cada uma. `--counts` acrescenta o número de linhas.

```bash

```

Detalha uma tabela: colunas com tipo e nulidade, índices e chaves estrangeiras. Mais rápido que abrir um cliente gráfico para conferir se a migration criou o que devia.

```bash

```

Abre o cliente de linha de comando do banco (`psql`, `mysql`) já conectado com as credenciais do `.env`. `php artisan db relatorios` abre outra conexão.

```bash
php artisan db:monitor --databases=pgsql --max=100
```

Verifica o número de conexões abertas e dispara o evento `DatabaseBusy` se passar do máximo. Agendado no scheduler, serve para receber um alerta antes de o banco recusar conexões.

### Busca vetorial

A busca comum (`where`, `like`, full-text) encontra **palavras**. A busca vetorial encontra **significado**: "vinho tinto encorpado da serra gaúcha" acha um texto sobre "Cabernet do Vale dos Vinhedos" mesmo sem nenhuma palavra em comum.

Como funciona:

1. **Embedding**: um modelo de IA (da OpenAI, Voyage, Gemini…) transforma um texto num vetor, uma lista de centenas ou milhares de números (por exemplo, 1536). Textos com significado parecido geram vetores próximos.
2. **Armazenamento**: o vetor de cada documento é gravado numa coluna do tipo `vector`, da extensão `pgvector` do PostgreSQL.
3. **Consulta**: a pergunta do usuário também vira vetor, e o banco ordena os documentos pela **distância** entre os vetores (a distância de cosseno é a mais comum). Os mais próximos são os mais parecidos.

Casos de uso: busca semântica no catálogo ou na base de ajuda, "produtos parecidos", agrupar tickets de suporte por assunto, e RAG (buscar os trechos relevantes de documentos para entregar a um modelo de IA responder com base neles).

```php [database/migrations/2026_11_09_140000_create_documentos_table.php]
return new class extends Migration
{
    public function up(): void
    {
        Schema::ensureVectorExtensionExists();                 // create extension if not exists vector

        Schema::create('documentos', function (Blueprint $table) {
            $table->id();
            $table->text('conteudo');
            $table->vector('embedding', dimensions: 1536);     // o tamanho do vetor do modelo usado
            $table->timestamps();
        });

        // índice HNSW: busca aproximada, rápida em milhões de linhas
        DB::statement('create index documentos_embedding_idx on documentos using hnsw (embedding vector_cosine_ops)');
    }
};
```

:version[Laravel 13+] O Query Builder busca por similaridade. Quando você passa um texto, o Laravel gera o embedding dele com o provedor de IA configurado; também é possível passar o vetor pronto (um array de floats):

```php [app/Http/Controllers/BuscaController.php]
$documentos = DB::table('documentos')
    ->whereVectorSimilarTo('embedding', 'Melhores vinícolas do Vale dos Vinhedos')
    ->limit(10)
    ->get();
```

Em versões anteriores, ou para controlar o SQL, a mesma busca com o operador de distância de cosseno do pgvector (`<=>`), passando o vetor da pergunta já gerado:

```php [app/Http/Controllers/BuscaController.php]
$vetor = '['.implode(',', $embeddingDaPergunta).']';

$documentos = DB::table('documentos')
    ->select('id', 'conteudo')
    ->selectRaw('1 - (embedding <=> ?::vector) as similaridade', [$vetor])
    ->orderByRaw('embedding <=> ?::vector', [$vetor])     // menor distância primeiro
    ->limit(10)
    ->get();
```

Cuidados: o vetor da pergunta e os dos documentos precisam vir **do mesmo modelo** (dimensões e "espaço" iguais); gerar embeddings custa uma chamada de API por texto, então gere ao salvar o documento (num job), não a cada busca; e a busca vetorial não substitui filtros exatos. Combine os dois: `where('loja_id', $loja)->whereVectorSimilarTo(...)`.
