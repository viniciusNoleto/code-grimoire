Filas tiram trabalho lento ou sujeito a falhas (e-mails, integrações, relatórios, processamento de arquivos) do ciclo da requisição. O controller só registra o job; um processo separado, o worker, executa depois.

### Conexões, filas e drivers

- **Conexão**: o serviço que guarda os jobs (`QUEUE_CONNECTION`): `database` (padrão no Laravel 11+), `redis`, `sqs`, `beanstalkd`, `sync` (executa na hora, útil em testes).
- **Fila**: uma lista dentro da conexão (`default`, `emails`, `relatorios`), usada para priorizar.

```bash
php artisan make:queue-table           # migration da tabela jobs (já existe em projetos novos)
php artisan make:queue-failed-table
php artisan make:queue-batches-table
```

### Criar um job

```bash
php artisan make:job ProcessarNotaFiscal
```

```php [app/Jobs/ProcessarNotaFiscal.php]
class ProcessarNotaFiscal implements ShouldQueue
{
    use Queueable;            // Laravel 11+: reúne Dispatchable, InteractsWithQueue, Queueable e SerializesModels

    public function __construct(public Pedido $pedido) {}

    public function handle(EmissorNfe $emissor): void       // dependências injetadas aqui
    {
        $nota = $emissor->emitir($this->pedido);
        $this->pedido->update(['nota_fiscal' => $nota->numero]);
    }

    public function failed(?Throwable $e): void              // depois de esgotar as tentativas
    {
        $this->pedido->user->notify(new FalhaNaNotaFiscal($this->pedido));
    }
}
```

::note{type="pitfall" title="Atenção"}
Models passados ao construtor são serializados só pelo id. Quando o job roda, o Model é buscado de novo no banco, com o estado atual, e sem os relacionamentos carregados que você tinha no momento do dispatch.
::

### Despachar

```php [app/Http/Controllers/PedidoController.php]
ProcessarNotaFiscal::dispatch($pedido);
ProcessarNotaFiscal::dispatch($pedido)->onQueue('fiscal')->onConnection('redis');
ProcessarNotaFiscal::dispatch($pedido)->delay(now()->addMinutes(10));
ProcessarNotaFiscal::dispatchIf($pedido->pago, $pedido);
ProcessarNotaFiscal::dispatchSync($pedido);            // executa agora, sem fila
ProcessarNotaFiscal::dispatch($pedido)->afterResponse(); // depois de enviar a resposta, no mesmo processo
dispatch(fn () => Cache::forget('vendas'));            // closure na fila
```

:version[Laravel 13+] Fila e conexão padrão por classe, num só lugar (`AppServiceProvider::boot()`):

```php [app/Providers/AppServiceProvider.php]
class AppServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        Queue::route(ProcessarNotaFiscal::class, connection: 'redis', queue: 'fiscal');
    }
}
```

### Tentativas, espera e timeout

```php [app/Jobs/ProcessarNotaFiscal.php]
class ProcessarNotaFiscal implements ShouldQueue
{
    public $tries = 5;                    // tentativas no total
    public $backoff = [10, 60, 300];      // segundos de espera entre tentativas (cresce)
    public $timeout = 120;                // segundos até matar o job
    public $maxExceptions = 3;            // falha antes se lançar 3 exceções
    public $failOnTimeout = true;
    public $deleteWhenMissingModels = true;   // Model apagado antes de rodar: descarta sem erro

    public function retryUntil(): DateTime { return now()->addHour(); }   // alternativa a $tries

    public function handle(): void
    {
        if ($this->sefazForaDoAr()) {
            $this->release(60);           // devolve à fila e tenta em 60s
            return;
        }
        if ($this->dadosInvalidos()) {
            $this->fail('Dados inválidos');   // falha definitiva, sem novas tentativas
        }
    }
}
```

:version[Laravel 13+] As mesmas configurações por atributos:

```php [app/Jobs/ProcessarNotaFiscal.php]
use Illuminate\Queue\Attributes\{Tries, Timeout, MaxExceptions, FailOnTimeout};

#[Tries(5)]
#[MaxExceptions(3)]
#[Timeout(120)]
#[FailOnTimeout]
class ProcessarNotaFiscal implements ShouldQueue { }
```

Jobs que falham vão para a tabela `failed_jobs`:

```bash
php artisan queue:failed               # lista
php artisan queue:retry all            # ou um uuid específico
php artisan queue:forget <uuid>
php artisan queue:prune-failed --hours=48
```

### Middleware de job

```php [app/Jobs/ProcessarNotaFiscal.php]
class ProcessarNotaFiscal implements ShouldQueue
{
    public function middleware(): array
    {
        return [
            new WithoutOverlapping($this->pedido->id),            // um job por pedido por vez
            new RateLimited('api-sefaz'),                          // limiter definido com RateLimiter::for
            (new ThrottlesExceptions(10, 5 * 60))->backoff(5),     // após 10 exceções, pausa 5 min
            Skip::when($this->pedido->cancelado),                  // descarta sem rodar
        ];
    }
}
```

### Jobs únicos

```php [app/Jobs/AtualizarIndiceDeBusca.php]
class AtualizarIndiceDeBusca implements ShouldQueue, ShouldBeUnique
{
    public $uniqueFor = 3600;                                  // trava por até 1 hora

    public function __construct(public Produto $produto) {}

    public function uniqueId(): string { return (string) $this->produto->id; }
}
```

Enquanto existir um job com o mesmo `uniqueId` na fila, novos dispatches são ignorados. `ShouldBeUniqueUntilProcessing` libera a trava quando o job começa a rodar, em vez de quando termina. A trava usa o cache, então o driver de cache precisa suportar locks ([seção 44.5](#cache-e-locks-locks-atômicos)).

:version[Laravel 13+] `#[UniqueFor(3600)]` substitui a propriedade, e `#[DebounceFor(30)]` (com `debounceId()`) faz o contrário de "único": mantém só o **último** dispatch dentro da janela, útil para reagir a muitas alterações seguidas.

### Cadeias e lotes

```php [app/Actions/FinalizarPedido.php]
// cadeia: um depois do outro; se um falha, os seguintes não rodam
Bus::chain([
    new ProcessarPagamento($pedido),
    new EmitirNotaFiscal($pedido),
    new EnviarConfirmacao($pedido),
])->catch(fn (Throwable $e) => Log::error('Cadeia falhou', ['erro' => $e->getMessage()]))
  ->dispatch();

// lote: em paralelo, com acompanhamento de progresso
$lote = Bus::batch(
    $clientes->map(fn ($c) => new ImportarCliente($c))->all()
)->then(fn (Batch $b) => Log::info('Importação concluída'))
 ->catch(fn (Batch $b, Throwable $e) => Log::error('Falha em um job'))
 ->finally(fn (Batch $b) => Cache::forget('importando'))
 ->allowFailures()
 ->name('Importação de clientes')
 ->dispatch();

$lote->id;  Bus::findBatch($id)->progress();   // 0 a 100
```

Jobs de lote usam a trait `Batchable` e podem checar `if ($this->batch()->cancelled()) return;`.

### Filas e transações

Se você despacha um job dentro de `DB::transaction()`, o worker pode pegá-lo **antes** do commit e não encontrar o registro. Duas soluções:

```php [app/Http/Controllers/PedidoController.php]
ProcessarNotaFiscal::dispatch($pedido)->afterCommit();   // espera o commit
```

Ou para todos os jobs de uma conexão:

```php [config/queue.php]
return [
    'connections' => [
        'redis' => [
            'driver' => 'redis',
            // ...
            'after_commit' => true,
        ],
    ],
];
```

### Workers em execução

```bash
php artisan queue:work redis --queue=alta,default,baixa --tries=3 --timeout=90 --max-time=3600 --memory=256
php artisan queue:listen        # desenvolvimento: recarrega o código a cada job (lento)
php artisan queue:restart       # após deploy: workers terminam o job atual e reiniciam
php artisan queue:monitor redis:default --max=100   # alerta quando a fila passa de 100
```

| Opção | Efeito |
| --- | --- |
| `--queue=alta,default` | Processa `alta` primeiro: prioridade por ordem |
| `--tries`, `--timeout`, `--backoff` | Padrões para jobs que não definem os seus |
| `--max-jobs`, `--max-time` | Reinicia o worker periodicamente (contém vazamento de memória) |
| `--sleep=3` | Espera quando a fila está vazia |
| `--stop-when-empty` | Termina quando não houver jobs (útil em containers) |

::note{type="pitfall" title="Atenção"}
O worker mantém o código carregado na memória. Sem `queue:restart` no deploy, ele continua rodando a versão antiga.
::

::note{type="pitfall" title="Cuidado"}
O `retry_after` da conexão (em `config/queue.php`) deve ser **maior** que o `timeout` do job mais longo. Caso contrário, o job é entregue a outro worker enquanto ainda roda e executa duas vezes.
::

Em produção, um gerenciador de processos (Supervisor, systemd) mantém os workers vivos ([seção 54.4](#deploy-workers-e-agendador)). Com Redis, o **Horizon** gerencia workers, balanceamento entre filas e oferece um painel com métricas e falhas.

### Jobs idempotentes

Um job pode rodar mais de uma vez (nova tentativa, worker reiniciado no meio). Escreva-o para que rodar duas vezes tenha o mesmo efeito que uma: verifique se o trabalho já foi feito, use `updateOrCreate`/`upsert`, envie chaves de idempotência para APIs de pagamento.
