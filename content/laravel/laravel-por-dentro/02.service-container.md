O Service Container é o objeto que cria as classes da aplicação e entrega a cada uma as dependências que ela pede. Quase tudo no Laravel (controllers, jobs, listeners, comandos, middlewares) é construído por ele.

### Injeção automática (autowiring)

Se a dependência é uma classe concreta, o container resolve sozinho, sem configuração, lendo os tipos do construtor via Reflection.

```php [app/Http/Controllers/RelatorioController.php]
namespace App\Http\Controllers;

use App\Models\Pedido;
use App\Services\GeradorDeRelatorio;
use Illuminate\Http\Request;

class RelatorioController extends Controller
{
    public function __construct(
        private GeradorDeRelatorio $gerador,     // injetado no construtor
    ) {}

    public function show(Request $request, Pedido $pedido)  // injeção no método + route model binding
    {
        return $this->gerador->para($pedido, $request->user());
    }
}
```

A injeção funciona no construtor de controllers, jobs, listeners, middlewares e comandos, e também nos métodos `handle()` de jobs, comandos e listeners, nos métodos de controllers e em closures de rota.

### `bind`, `singleton`, `scoped` e `instance`

Você só precisa registrar algo no container quando ele não consegue adivinhar: interfaces, classes que precisam de valores primitivos (chaves de API) ou objetos que devem ser compartilhados. O registro fica no `register()` de um Service Provider, normalmente o `AppServiceProvider`. Os quatro métodos diferem em **quantas vezes o objeto é criado** e **por quanto tempo ele é reaproveitado**.

| Método | Quantas instâncias | Quem cria o objeto | Uso típico |
| --- | --- | --- | --- |
| `bind(Abstrato, Closure\|Concreto)` | Uma nova a cada resolução | O container, na hora em que é pedido | Objetos com estado próprio |
| `singleton(...)` | Uma só durante toda a vida do processo | O container, na primeira vez em que é pedido | Clientes de API, serviços sem estado |
| `scoped(...)` | Uma por requisição ou job | O container, na primeira vez dentro de cada requisição/job | Serviços com estado da requisição; seguro no Octane e nas filas |
| `instance(Abstrato, $objeto)` | O objeto que você passou | Você, antes de registrar | Objeto já construído, mocks em testes |

#### `bind`: um objeto novo a cada pedido

Cada `app(Classe::class)`, cada construtor que pede a classe e cada injeção em método recebe um objeto **diferente**. É o comportamento do autowiring; você só escreve o `bind` quando precisa ensinar o container a montar o objeto (uma interface, um parâmetro primitivo).

Caso de uso: um montador de relatório que acumula linhas. Se dois serviços o recebessem compartilhado, um veria as linhas do outro.

```php [app/Providers/AppServiceProvider.php]
namespace App\Providers;

use App\Services\MontadorDeRelatorio;
use Illuminate\Contracts\Foundation\Application;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->bind(MontadorDeRelatorio::class, function (Application $app) {
            return new MontadorDeRelatorio(formato: config('relatorios.formato'));
        });
    }
}
```

```php [app/Services/ExportacaoService.php]
$a = app(MontadorDeRelatorio::class);
$b = app(MontadorDeRelatorio::class);
$a === $b;   // false: dois objetos independentes
```

#### `singleton`: um só objeto para o processo inteiro

A closure roda **uma vez**, na primeira resolução; daí em diante todo mundo recebe o mesmo objeto. Serve para objetos caros de construir e que não guardam dados de um usuário específico: um cliente HTTP configurado, um SDK de pagamento, um parser com tabelas carregadas.

```php [app/Providers/AppServiceProvider.php]
class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->singleton(GatewayPagamento::class, function (Application $app) {
            return new GatewayPagamento(
                chave: config('services.pagamento.key'),
                http: $app->make(HttpClient::class),
            );
        });
    }
}
```

"Vida do processo" muda de significado conforme o servidor. No PHP-FPM tradicional, o processo morre ao fim de cada requisição, então singleton e scoped se comportam igual. No **Octane** e nos **workers de fila** (`queue:work`), o processo atende centenas de requisições/jobs: um singleton criado na primeira continua vivo em todas as seguintes.

#### `scoped`: um objeto por requisição ou job

Igual ao singleton dentro de uma requisição (ou de um job), mas o Laravel descarta a instância quando começa a próxima requisição no Octane ou o próximo job no worker. Use quando o objeto guarda algo que pertence **a quem está sendo atendido**: o usuário atual, o tenant, o carrinho.

```php [app/Providers/AppServiceProvider.php]
class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // recriado a cada requisição/job; dentro dela, todos recebem o mesmo carrinho
        $this->app->scoped(CarrinhoAtual::class, fn (Application $app) => new CarrinhoAtual(
            $app['request']->user(),
        ));
    }
}
```

::note{type="pitfall" title="Singleton ou scoped?"}
Se o objeto lê o usuário, o tenant, o idioma ou qualquer coisa da requisição, ele **não pode** ser singleton: no Octane, o segundo usuário receberia o objeto montado com os dados do primeiro. Nessa situação use `scoped`. Singleton só para o que é igual para todos.
::

#### `instance`: um objeto que você já tem

Não há closure: você constrói o objeto e entrega pronto. Ele passa a ser devolvido em toda resolução, como um singleton. A diferença é que o singleton é **preguiçoso** (só constrói se alguém pedir) e o `instance` já gastou o trabalho de construir. O uso mais comum é em testes, para trocar um serviço por um dublê.

```php [tests/Feature/CheckoutTest.php]
class CheckoutTest extends TestCase
{
    public function test_cobra_o_cliente(): void
    {
        $fake = new GatewayPagamentoFake();
        $this->app->instance(GatewayPagamento::class, $fake);   // todo GatewayPagamento agora é o fake

        $this->post('/checkout')->assertOk();

        $this->assertCount(1, $fake->cobrancas);
    }
}
```

Variações úteis: `bindIf()`, `singletonIf()` e `scopedIf()` só registram se ainda não houver registro para aquela chave (comum em pacotes, para não sobrescrever a escolha da aplicação).

### Interface para implementação

Ligar uma interface a uma classe concreta permite trocar a implementação sem mexer em quem a usa.

```php [app/Providers/AppServiceProvider.php]
class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->bind(Notificador::class, NotificadorWhatsApp::class);
    }
}
```

```php [app/Services/AvisoService.php]
class AvisoService
{
    public function __construct(private Notificador $notificador) {}   // recebe NotificadorWhatsApp
}
```

:version[Laravel 12+] O mesmo pode ser declarado com atributos, sem provider:

```php [app/Contracts/Notificador.php]
namespace App\Contracts;

use App\Services\NotificadorFake;
use App\Services\NotificadorWhatsApp;
use Illuminate\Container\Attributes\Bind;

#[Bind(NotificadorWhatsApp::class)]
#[Bind(NotificadorFake::class, environments: ['local', 'testing'])]
interface Notificador {}
```

```php [app/Services/GatewayPagamento.php]
use Illuminate\Container\Attributes\Singleton;

#[Singleton]        // ou #[Scoped]
class GatewayPagamento {}
```

### Binding contextual

O binding comum (`bind(Interface, Classe)`) vale para a aplicação inteira: **todo** construtor que pede a interface recebe a mesma implementação. O binding contextual responde a outra pergunta: "quando **esta** classe pedir **aquela** dependência, entregue **isto**". A frase é lida literalmente no código: `when(Quem)->needs(OQue)->give(Isto)`.

Caso de uso: `FotoController` e `VideoController` recebem os dois um `Filesystem` no construtor, mas fotos ficam no disco local e vídeos no S3. Sem binding contextual você teria que criar duas interfaces só para diferenciar, ou chamar `Storage::disk()` dentro de cada controller.

```php [app/Providers/AppServiceProvider.php]
namespace App\Providers;

use App\Http\Controllers\FotoController;
use App\Http\Controllers\UploadController;
use App\Http\Controllers\VideoController;
use App\Services\GatewayPagamento;
use App\Services\PainelDeRelatorios;
use Illuminate\Contracts\Filesystem\Filesystem;
use Illuminate\Support\Facades\Storage;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // FotoController pediu Filesystem → disco local
        $this->app->when(FotoController::class)
            ->needs(Filesystem::class)
            ->give(fn () => Storage::disk('local'));

        // a mesma regra para várias classes de uma vez
        $this->app->when([VideoController::class, UploadController::class])
            ->needs(Filesystem::class)
            ->give(fn () => Storage::disk('s3'));

        // parâmetro primitivo: o nome da variável, com $
        $this->app->when(GatewayPagamento::class)
            ->needs('$chave')
            ->giveConfig('services.pagamento.key');      // atalho para config('services.pagamento.key')

        $this->app->when(GatewayPagamento::class)
            ->needs('$timeout')
            ->give(10);                                  // valor fixo

        // parâmetro variádico ou array com todas as classes de uma tag
        $this->app->when(PainelDeRelatorios::class)
            ->needs('$relatorios')
            ->giveTagged('relatorios');
    }
}
```

```php [app/Services/GatewayPagamento.php]
class GatewayPagamento
{
    // $chave e $timeout são primitivos: sem o binding contextual o container não sabe o que passar
    public function __construct(private string $chave, private int $timeout) {}
}
```

| Método | O que entrega |
| --- | --- |
| `give(Classe::class)` | Uma instância daquela classe, resolvida pelo container |
| `give(fn ($app) => ...)` | O retorno da closure (montagem manual) |
| `give($valor)` | Um valor fixo, para parâmetros primitivos |
| `giveConfig('arquivo.chave')` | O valor da configuração |
| `giveTagged('tag')` | Todas as classes registradas com aquela tag |

### Atributos contextuais

:version[Laravel 11+] Atributos contextuais fazem o mesmo trabalho do binding contextual, mas a decisão fica **no próprio parâmetro**, sem escrever nada no provider. Cada atributo diz de onde tirar o valor daquele parâmetro.

```php [app/Services/RelatorioService.php]
namespace App\Services;

use Illuminate\Container\Attributes\{Cache, Config, DB, Log, Storage, Tag};
use Illuminate\Contracts\Cache\Repository;
use Illuminate\Contracts\Filesystem\Filesystem;
use Illuminate\Database\Connection;
use Psr\Log\LoggerInterface;

class RelatorioService
{
    public function __construct(
        #[Config('app.timezone')] private string $fuso,
        #[Storage('s3')] private Filesystem $arquivos,
        #[DB('pgsql')] private Connection $conexao,
        #[Log('daily')] private LoggerInterface $log,
        #[Cache('redis')] private Repository $cache,
        #[Tag('relatorios')] private iterable $relatorios,
    ) {}
}
```

| Atributo | Injeta | Equivale a |
| --- | --- | --- |
| `#[Config('app.timezone')]` | O valor de uma configuração | `config('app.timezone')` |
| `#[Storage('s3')]` | O disco de arquivos com aquele nome | `Storage::disk('s3')` |
| `#[DB('pgsql')]` | A conexão de banco com aquele nome | `DB::connection('pgsql')` |
| `#[Log('daily')]` | O canal de log | `Log::channel('daily')` |
| `#[Cache('redis')]` | O store de cache | `Cache::store('redis')` |
| `#[Auth('web')]` | O guard de autenticação | `Auth::guard('web')` |
| `#[CurrentUser]` | O usuário autenticado (o model) | `auth()->user()` |
| `#[RouteParameter('pedido')]` | O parâmetro da rota atual | `$request->route('pedido')` |
| `#[Context('tenant_id')]` | Um valor do `Context` da requisição | `Context::get('tenant_id')` |
| `#[Tag('relatorios')]` | Todas as classes da tag | `app()->tagged('relatorios')` |
| `#[Give(Classe::class)]` | Uma implementação específica para aquele parâmetro | `when(...)->needs(...)->give(Classe::class)` |

Funcionam em qualquer lugar onde o container injeta, inclusive closures de rota:

```php [routes/web.php]
use Illuminate\Container\Attributes\CurrentUser;

Route::get('/perfil', fn (#[CurrentUser] User $user) => $user)->middleware('auth');
```

Quando preferir cada um: atributo quando a escolha é da própria classe e não muda; binding contextual no provider quando a escolha é da aplicação (a classe vem de um pacote que você não edita, ou a decisão depende de ambiente).

### Resolver manualmente

```php [app/Http/Controllers/CheckoutController.php]
$gateway = app(GatewayPagamento::class);                 // helper
$gateway = app()->make(GatewayPagamento::class);
$gateway = resolve(GatewayPagamento::class);
$relatorio = app()->makeWith(Relatorio::class, ['mes' => 10]);  // passa parâmetros extras

app()->call([$servico, 'executar']);   // chama um método injetando as dependências dele
```

::note{type="pitfall" title="Cuidado"}
Chamar `app()` espalhado pelo código esconde dependências (é o padrão *service locator*). Prefira receber no construtor; use `app()` em pontos de borda, como closures e helpers.
::

### Tags, extend e eventos de resolução

São três ganchos para trabalhar com o que já está registrado, sem mudar as classes.

#### `tag` e `tagged`: agrupar implementações

Uma tag é um rótulo que reúne várias classes. Depois você pede "todas as classes com este rótulo" de uma vez. Caso de uso: um painel que mostra todos os relatórios disponíveis. Para incluir um relatório novo basta acrescentá-lo à tag; o painel não muda.

```php [app/Providers/AppServiceProvider.php]
class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->tag([RelatorioVendas::class, RelatorioEstoque::class], 'relatorios');

        $this->app->bind(PainelDeRelatorios::class, fn (Application $app) => new PainelDeRelatorios(
            $app->tagged('relatorios'),   // iterável, cada item já resolvido pelo container
        ));
    }
}
```

#### `extend`: decorar um serviço já registrado

`extend` recebe o objeto que o container acabou de montar e devolve outro no lugar. Serve para o padrão *decorator*: envolver o serviço original com comportamento extra (log, cache, métricas) sem editar a classe nem o registro original, que pode até vir de um pacote.

```php [app/Providers/AppServiceProvider.php]
class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // quem pedir Notificador recebe NotificadorComLog, que repassa ao original
        $this->app->extend(Notificador::class, fn (Notificador $original, Application $app) => new NotificadorComLog($original, $app->make(LoggerInterface::class)));
    }
}
```

#### `resolving` e `afterResolving`: reagir quando algo é criado

São callbacks que rodam toda vez que o container constrói um objeto daquele tipo. Diferente do `extend`, eles **não trocam** o objeto: só podem configurá-lo. Úteis para ajustar algo em todas as instâncias de uma interface, inclusive implementações que você não conhece.

```php [app/Providers/AppServiceProvider.php]
class AppServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        // toda implementação de Notificador sai com o idioma configurado
        $this->app->resolving(Notificador::class, fn (Notificador $n, Application $app) => $n->setLocale('pt_BR'));

        // roda depois de todos os callbacks resolving
        $this->app->afterResolving(Notificador::class, fn (Notificador $n) => $n->validarConfiguracao());
    }
}
```

| Gancho | Troca o objeto? | Quando usar |
| --- | --- | --- |
| `extend` | Sim (devolve o substituto) | Envolver o serviço com outro (decorator) |
| `resolving` | Não (só altera) | Configurar toda instância recém-criada |
| `afterResolving` | Não | Configuração que depende de outro `resolving` já ter rodado |
