Migrations são o controle de versão do banco: cada arquivo descreve uma alteração no schema e pode ser aplicado ou desfeito. Assim, todos os ambientes chegam ao mesmo schema rodando os mesmos arquivos.

### Comandos

```bash
php artisan make:migration create_pedidos_table
php artisan make:migration add_cupom_to_pedidos_table      # o nome sugere create ou table

php artisan migrate                    # aplica as pendentes
php artisan migrate --pretend          # mostra o SQL sem executar
php artisan migrate --force            # em produção (pula a confirmação)
php artisan migrate:status
php artisan migrate:rollback --step=1  # desfaz o último lote
php artisan migrate:fresh --seed       # APAGA tudo e recria (só em desenvolvimento)
php artisan schema:dump --prune        # junta as migrations antigas num arquivo de schema
```

### Estrutura

```php [database/migrations/2026_11_09_120000_create_pedidos_table.php]
use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;

return new class extends Migration
{
    public function up(): void
    {
        Schema::create('pedidos', function (Blueprint $table) {
            $table->id();                                         // bigint autoincremento
            $table->foreignId('cliente_id')->constrained()->cascadeOnDelete();
            $table->string('numero', 20)->unique();
            $table->decimal('total', 10, 2)->default(0);
            $table->string('status')->default('pendente')->index();
            $table->jsonb('metadados')->nullable();
            $table->timestamp('pago_em')->nullable();
            $table->timestamps();                                 // created_at e updated_at
            $table->softDeletes();                                // deleted_at
        });
    }

    public function down(): void
    {
        Schema::dropIfExists('pedidos');
    }
};
```

### Tipos de coluna

Cada método do `Blueprint` cria uma coluna com um tipo do banco. A tabela mostra o tipo gerado no PostgreSQL (e no MySQL quando é diferente e relevante). Os exemplos vão dentro de `Schema::create()` ou `Schema::table()`, numa migration como a da seção anterior.

#### Chaves primárias

| Método | PostgreSQL | O que cria |
| --- | --- | --- |
| `id()` | `bigserial primary key` | Coluna `id`, inteiro grande que se autoincrementa. Padrão de toda tabela |
| `bigIncrements('id')` | `bigserial primary key` | O mesmo que `id()`, mas com nome escolhido |
| `increments('id')` | `serial primary key` | Inteiro de 4 bytes autoincrementado (até ~2,1 bilhões) |
| `smallIncrements('id')` | `smallserial primary key` | Inteiro de 2 bytes (até 32.767): tabelas de domínio pequenas |
| `tinyIncrements('id')` | `smallserial primary key` | 1 byte no MySQL (até 255); no PostgreSQL vira `smallserial` |
| `mediumIncrements('id')` | `serial primary key` | 3 bytes no MySQL; no PostgreSQL vira `serial` |
| `uuid('id')` | `uuid` | UUID de 36 caracteres; vira chave com `->primary()` |
| `ulid('id')` | `char(26)` | ULID, ordenável pelo tempo; vira chave com `->primary()` |

`id()` × `increments()`: só muda o tamanho do inteiro. Use `id()` sempre; o ganho de espaço do `increments` raramente compensa o risco de estourar o limite. `uuid` × `ulid`: o UUID v4 é aleatório e espalha as inserções pelo índice; o ULID (e o UUID v7, que o Laravel gera por padrão no `HasUuids`) começa pelo horário, então registros novos vão para o fim do índice, o que é mais rápido para inserir e permite ordenar por criação.

```php [database/migrations/2026_11_09_120000_create_arquivos_table.php]
$table->ulid('id')->primary();     // chave ULID em vez de inteiro
```

#### Chaves estrangeiras

| Método | PostgreSQL | O que cria |
| --- | --- | --- |
| `foreignId('cliente_id')` | `bigint` | Coluna para apontar para um `id()`. Sozinho **não** cria a FK: precisa de `->constrained()` |
| `foreignIdFor(Cliente::class)` | `bigint` | Igual, mas deduz o nome (`cliente_id`) e o tipo a partir do Model |
| `foreignUuid('cliente_id')` | `uuid` | Coluna para apontar para uma chave `uuid` |
| `foreignUlid('cliente_id')` | `char(26)` | Coluna para apontar para uma chave `ulid` |
| `unsignedBigInteger('cliente_id')` | `bigint` | Forma antiga; sem os atalhos `constrained()` |

`foreignId` × `foreignIdFor`: o resultado é o mesmo; `foreignIdFor` lê o Model e escolhe sozinho entre `bigint`, `uuid` e `ulid` conforme a chave do Model. O tipo da coluna estrangeira precisa ser **igual** ao da chave que ela referencia.

#### Texto

| Método | PostgreSQL | MySQL | Uso |
| --- | --- | --- | --- |
| `char('uf', 2)` | `char(2)` | `char(2)` | Tamanho **fixo**: completa com espaços. Siglas, códigos de tamanho constante |
| `string('nome', 100)` | `varchar(100)` | `varchar(100)` | Texto curto com limite (padrão 255). Nomes, e-mails, títulos |
| `tinyText('resumo')` | `text` | `tinytext` (255 bytes) | Raramente útil |
| `text('descricao')` | `text` | `text` (64 KB) | Texto longo sem limite definido |
| `mediumText('conteudo')` | `text` | `mediumtext` (16 MB) | Artigos, HTML |
| `longText('log')` | `text` | `longtext` (4 GB) | Conteúdo muito grande |

`string` × `text`: `string` tem limite e pode ser indexado inteiro sem cuidado especial; `text` não tem limite e, no MySQL, não aceita índice comum nem `default`. No PostgreSQL, `varchar(n)` e `text` têm o mesmo desempenho, e `tinyText`/`mediumText`/`longText` viram todos `text`; a diferença entre eles só existe no MySQL. `char` × `string`: `char` reserva sempre o tamanho todo; só faz sentido quando todo valor tem exatamente aquele comprimento.

#### Números inteiros

| Método | PostgreSQL | Faixa (com sinal) |
| --- | --- | --- |
| `tinyInteger('nota')` | `smallint` | MySQL: -128 a 127 (1 byte); PostgreSQL não tem tipo de 1 byte |
| `smallInteger('ordem')` | `smallint` | -32.768 a 32.767 |
| `mediumInteger('x')` | `integer` | MySQL: ~±8 milhões (3 bytes) |
| `integer('estoque')` | `integer` | ~±2,1 bilhões |
| `bigInteger('visualizacoes')` | `bigint` | ~±9,2 quintilhões |
| `unsignedInteger('estoque')` | `integer` | MySQL: 0 a ~4,2 bilhões. No PostgreSQL, *unsigned* é ignorado |
| `unsignedBigInteger('x')` | `bigint` | Idem, versão grande |

Escolha pelo maior valor que a coluna pode atingir com folga. `unsigned*` dobra o limite positivo no MySQL, mas não existe no PostgreSQL: lá, para impedir negativos, use uma *check constraint*.

#### Números decimais

| Método | PostgreSQL | Precisão |
| --- | --- | --- |
| `decimal('total', 10, 2)` | `numeric(10, 2)` | **Exata**: 10 dígitos no total, 2 depois da vírgula (até 99.999.999,99) |
| `float('nota')` | `double precision` | Aproximada (ponto flutuante); `float('x', 24)` gera `real` |
| `double('latitude')` | `double precision` | Aproximada, 15 dígitos significativos |

`decimal` × `float`/`double`: ponto flutuante não representa exatamente valores como 0,1, e somas acumulam erro (`0.1 + 0.2 = 0.30000000000000004`). Para dinheiro, quantidades e qualquer valor que precise bater centavo a centavo, use sempre `decimal`. `float`/`double` servem para medidas científicas, coordenadas, notas de ranking.

#### Booleano

| Método | PostgreSQL | MySQL |
| --- | --- | --- |
| `boolean('ativo')` | `boolean` | `tinyint(1)` |

No MySQL o valor volta do banco como `0`/`1`; declare o cast `'boolean'` no Model para receber `true`/`false` ([seção 16.8](#criar-e-configurar-casts)).

#### Datas e horas

| Método | PostgreSQL | Guarda |
| --- | --- | --- |
| `date('nascimento')` | `date` | Só a data (`2026-11-09`) |
| `time('abre_as')` | `time(0) without time zone` | Só a hora (`08:30:00`) |
| `timeTz('abre_as')` | `time(0) with time zone` | Hora com fuso |
| `dateTime('agendado_para')` | `timestamp(0) without time zone` | Data e hora, sem fuso |
| `dateTimeTz('agendado_para')` | `timestamp(0) with time zone` | Data e hora com fuso |
| `timestamp('pago_em')` | `timestamp(0) without time zone` | Data e hora, sem fuso |
| `timestampTz('pago_em')` | `timestamp(0) with time zone` | Data e hora com fuso |
| `year('ano_fabricacao')` | `integer` | Só o ano |

Os métodos aceitam a precisão de frações de segundo: `timestamp('x', precision: 6)` guarda microssegundos.

`dateTime` × `timestamp`: no PostgreSQL geram exatamente o mesmo tipo. No MySQL são diferentes: `timestamp` guarda em UTC e converte para o fuso da conexão ao ler, mas só vai de 1970 a 2038; `dateTime` guarda o valor como foi escrito e vai do ano 1000 ao 9999. Para datas de nascimento ou eventos distantes, `date`/`dateTime`. Variantes `Tz` × sem `Tz`: com fuso, o PostgreSQL converte tudo para UTC ao gravar e para o fuso da sessão ao ler, o que evita ambiguidade se servidores rodam em fusos diferentes. Se a aplicação sempre grava em UTC (o padrão do Laravel, `APP_TIMEZONE=UTC`), as duas funcionam.

#### Colunas prontas do framework

| Método | Cria | Usado por |
| --- | --- | --- |
| `timestamps()` | `created_at` e `updated_at`, `timestamp` *nullable* | Eloquent preenche sozinho |
| `timestampsTz()` | O mesmo, com fuso | |
| `softDeletes()` | `deleted_at`, `timestamp` *nullable* | Trait `SoftDeletes` ([seção 22](#excluir-e-soft-delete)) |
| `softDeletesTz()` | O mesmo, com fuso | |
| `rememberToken()` | `remember_token`, `varchar(100)` *nullable* | "Lembrar de mim" no login |

#### JSON

| Método | PostgreSQL | MySQL |
| --- | --- | --- |
| `json('opcoes')` | `json` (guarda o texto como veio) | `json` |
| `jsonb('opcoes')` | `jsonb` (guarda já decomposto, em binário) | `json` |

`json` × `jsonb` no PostgreSQL: `json` preserva o texto exato (espaços, ordem das chaves, chaves duplicadas) e precisa reinterpretá-lo a cada consulta. `jsonb` é um pouco mais lento para gravar, mas muito mais rápido para consultar, aceita índices GIN e operadores como `@>`. Prefira `jsonb` sempre, a menos que precise do texto original byte a byte.

#### Listas de valores

| Método | PostgreSQL | MySQL |
| --- | --- | --- |
| `enum('status', ['pendente', 'pago'])` | `varchar(255)` com `check (status in (...))` | `enum('pendente','pago')` |
| `set('dias', ['seg', 'ter'])` | Não suportado | `set(...)`: vários valores da lista numa coluna |

Acrescentar um valor ao `enum` exige migration com `change()`. Uma alternativa mais flexível é `string('status')` com um enum PHP e o cast no Model, deixando a lista de valores no código.

#### Relações polimórficas

| Método | Cria |
| --- | --- |
| `morphs('comentavel')` | `comentavel_id` (`bigint`) + `comentavel_type` (`varchar`) + índice composto |
| `nullableMorphs('comentavel')` | O mesmo, aceitando `null` |
| `uuidMorphs('comentavel')` | `comentavel_id` como `uuid` |
| `nullableUuidMorphs('comentavel')` | O mesmo, aceitando `null` |
| `ulidMorphs('comentavel')` | `comentavel_id` como `char(26)` |
| `nullableUlidMorphs('comentavel')` | O mesmo, aceitando `null` |

Escolha a variante conforme o tipo da chave dos Models que podem ser o "dono" ([seção 26](#definir-relacionamentos)).

#### Outros tipos

| Método | PostgreSQL | Uso |
| --- | --- | --- |
| `binary('assinatura')` | `bytea` | Dados binários pequenos (prefira arquivos no storage) |
| `ipAddress('ip')` | `inet` | Endereço IPv4/IPv6, com operadores de rede no PostgreSQL |
| `macAddress('mac')` | `macaddr` | Endereço MAC |
| `geometry('area')` | `geometry` (PostGIS) | Formas geométricas planas |
| `geography('local', subtype: 'point')` | `geography` (PostGIS) | Pontos e áreas na superfície da Terra |
| `vector('embedding', dimensions: 1536)` | `vector(1536)` (pgvector) | Embeddings para busca semântica ([seção 14.8](#db-transacoes-e-seeders-busca-vetorial)) |

#### Métodos que se encadeiam nas colunas

Depois de criar a coluna, você encadeia métodos que ajustam a coluna, criam índices ou definem chaves estrangeiras. Nem todo método vale para toda coluna:

| Método | O que faz | Pode ser usado em | Detalhes |
| --- | --- | --- | --- |
| `nullable()` | Aceita `NULL` | Qualquer coluna | [13.4](#migrations-modificadores-de-coluna) |
| `default($valor)` | Valor quando o `INSERT` não informa | Qualquer coluna (no MySQL, não em `text`/`json`) | [13.4](#migrations-modificadores-de-coluna) |
| `useCurrent()` | Padrão `CURRENT_TIMESTAMP` | `timestamp`, `dateTime` e variantes | [13.4](#migrations-modificadores-de-coluna) |
| `useCurrentOnUpdate()` | Atualiza para agora em todo `UPDATE` | `timestamp`, `dateTime` (só MySQL) | [13.4](#migrations-modificadores-de-coluna) |
| `unsigned()` | Sem sinal | Colunas inteiras (só MySQL) | [13.4](#migrations-modificadores-de-coluna) |
| `autoIncrement()` | Autoincremento | Colunas inteiras | [13.4](#migrations-modificadores-de-coluna) |
| `comment('texto')` | Comentário na coluna | Qualquer coluna (MySQL e PostgreSQL) | [13.4](#migrations-modificadores-de-coluna) |
| `after('coluna')`, `first()` | Posição da coluna | Qualquer coluna, só MySQL/MariaDB | [13.4](#migrations-modificadores-de-coluna) |
| `charset()`, `collation()` | Codificação e ordenação de texto | `char`, `string`, `text` | [13.4](#migrations-modificadores-de-coluna) |
| `storedAs('expr')`, `virtualAs('expr')` | Coluna calculada | Qualquer tipo | [13.4](#migrations-modificadores-de-coluna) |
| `change()` | Altera uma coluna existente | Qualquer coluna, só em `Schema::table` | [13.5](#migrations-alterar-tabelas-e-colunas) |
| `primary()` | Torna a coluna chave primária | Qualquer coluna (comum em `uuid`/`ulid`) | [13.6](#migrations-índices) |
| `unique()` | Índice único | Qualquer coluna indexável | [13.6](#migrations-índices) |
| `index()` | Índice comum | Qualquer coluna indexável | [13.6](#migrations-índices) |
| `fullText()` | Índice de busca textual | `string`, `text` | [13.6](#migrations-índices) |
| `spatialIndex()` | Índice espacial | `geometry`, `geography` | [13.6](#migrations-índices) |
| `constrained()` | Cria a FK para a tabela deduzida do nome | **Só** `foreignId`, `foreignIdFor`, `foreignUuid`, `foreignUlid` | [13.7](#migrations-chaves-estrangeiras) |
| `cascadeOnDelete()` | Apaga os filhos junto com o pai | Depois de `constrained()` ou `foreign()->references()` | [13.7](#migrations-chaves-estrangeiras) |
| `nullOnDelete()` | Põe `NULL` na FK ao apagar o pai | Idem; a coluna precisa ser `nullable()` | [13.7](#migrations-chaves-estrangeiras) |
| `restrictOnDelete()` | Impede apagar o pai com filhos | Idem | [13.7](#migrations-chaves-estrangeiras) |
| `noActionOnDelete()` | Comportamento padrão do banco (como restrict, checado no fim) | Idem | [13.7](#migrations-chaves-estrangeiras) |
| `cascadeOnUpdate()`, `restrictOnUpdate()`, `nullOnUpdate()` | O mesmo, quando a chave do pai muda | Idem | [13.7](#migrations-chaves-estrangeiras) |

A ordem importa em um caso: os modificadores da coluna (`nullable`, `default`) vêm **antes** de `constrained()`, porque depois dele a cadeia passa a configurar a FK, não mais a coluna.

```php [database/migrations/2026_11_09_120000_create_pedidos_table.php]
$table->foreignId('cupom_id')->nullable()->constrained()->nullOnDelete();   // certo
$table->foreignId('cupom_id')->constrained()->nullable();                   // nullable não pega na coluna
```

### Modificadores de coluna

Modificadores ajustam a coluna que você está criando (ou alterando com `change()`). Encadeie quantos quiser depois do tipo.

```php [database/migrations/2026_11_09_130000_create_produtos_table.php]
Schema::create('produtos', function (Blueprint $table) {
    $table->id();
    $table->string('sku', 30)->unique()->comment('Código interno do estoque');
    $table->string('descricao')->nullable();
    $table->unsignedInteger('estoque')->default(0);
    $table->boolean('ativo')->default(true);
    $table->timestamp('importado_em')->useCurrent();
    $table->decimal('preco', 10, 2);
    $table->decimal('preco_com_imposto', 10, 2)->storedAs('preco * 1.1');
    $table->string('nome')->collation('pt-BR-x-icu');
});
```

| Modificador | Efeito | Exemplo de uso |
| --- | --- | --- |
| `nullable()` | Permite `NULL`. Sem ele, toda coluna é `NOT NULL` | Campos opcionais: `descricao`, `pago_em` |
| `default($v)` | Valor quando o `INSERT` não informa a coluna | `default(0)`, `default('pendente')`, `default(true)` |
| `default(new Expression('...'))` | Padrão calculado pelo banco | `default(new Expression('gen_random_uuid()'))` |
| `useCurrent()` | Padrão `CURRENT_TIMESTAMP` | Data de importação preenchida pelo banco |
| `useCurrentOnUpdate()` | MySQL: atualiza para agora a cada `UPDATE` da linha | `atualizado_em` controlado pelo banco |
| `unsigned()` | MySQL: só valores ≥ 0, com o dobro do limite | Contadores, estoque |
| `autoIncrement()` | Coluna inteira autoincrementada, sem ser `id()` | Número sequencial de nota |
| `comment('…')` | Documenta a coluna no próprio banco | Colunas com significado não óbvio |
| `storedAs('expr')` | Coluna gerada, calculada e gravada pelo banco | Preço com imposto, nome completo |
| `virtualAs('expr')` | MySQL: coluna gerada calculada na leitura, sem ocupar espaço | Idem, quando espaço importa |
| `charset('utf8mb4')`, `collation('…')` | Codificação e regra de ordenação/comparação | Ordenar nomes com acento corretamente |
| `after('coluna')`, `first()` | MySQL/MariaDB: posição da coluna nova na tabela | Organização visual; não afeta desempenho |
| `invisible()` | MySQL: coluna fora do `select *` | Colunas internas |

`nullable()` × `default()`: `nullable` permite que a coluna fique sem valor; `default` garante que ela sempre tenha um. Uma coluna pode ter os dois (`nullable()->default('x')`): o `INSERT` sem a coluna grava `'x'`, mas um `INSERT` explícito com `null` grava `null`.

`useCurrent()` × `timestamps()`: os `created_at`/`updated_at` do `timestamps()` são preenchidos pelo **Eloquent**, no PHP. `useCurrent()` faz o **banco** preencher, e funciona até em `INSERT` feito fora do Laravel.

`storedAs` × `virtualAs`: a coluna `stored` é calculada na gravação e ocupa espaço, mas pode ser indexada; a `virtual` é calculada a cada leitura. O PostgreSQL só tem a versão `stored`.

### Alterar tabelas e colunas

Para mudar uma tabela que já existe, crie uma migration nova com `Schema::table()` (não edite a migration antiga) e descreva só a diferença:

```bash
php artisan make:migration add_cupom_to_pedidos_table
```

```php [database/migrations/2026_11_10_090000_add_cupom_to_pedidos_table.php]
return new class extends Migration
{
    public function up(): void
    {
        Schema::table('pedidos', function (Blueprint $table) {
            // acrescentar colunas
            $table->string('cupom', 8)->nullable()->after('numero');   // after só tem efeito no MySQL
            $table->timestamp('enviado_em')->nullable();

            // alterar uma coluna existente
            $table->string('numero', 30)->unique()->change();

            // renomear
            $table->renameColumn('obs', 'observacao');
        });
    }

    public function down(): void
    {
        Schema::table('pedidos', function (Blueprint $table) {
            $table->renameColumn('observacao', 'obs');
            $table->string('numero', 20)->unique()->change();
            $table->dropColumn(['cupom', 'enviado_em']);
        });
    }
};
```

| Operação | Código | Observação |
| --- | --- | --- |
| Adicionar coluna | `$table->tipo('nome')` dentro de `Schema::table` | Em tabela com dados, use `nullable()` ou `default()` |
| Alterar tipo/tamanho/modificadores | `$table->string('numero', 30)->change()` | Reescreve a definição inteira da coluna |
| Renomear coluna | `$table->renameColumn('de', 'para')` | |
| Remover coluna | `$table->dropColumn('cupom')` ou `dropColumn(['a', 'b'])` | Remove os dados junto |
| Remover colunas prontas | `dropTimestamps()`, `dropSoftDeletes()`, `dropRememberToken()`, `dropMorphs('alvo')` | |
| Renomear tabela | `Schema::rename('pedidos', 'encomendas')` | Fora do `Schema::table` |
| Remover tabela | `Schema::drop('pedidos')`, `Schema::dropIfExists('pedidos')` | |
| Verificar | `Schema::hasTable('pedidos')`, `Schema::hasColumn('pedidos', 'cupom')` | Útil em migrations idempotentes |

::note{type="pitfall" title="Atenção"}
Ao usar `change()`, repita **todos** os modificadores que a coluna deve manter (`nullable`, `default`, `comment`…). O `change()` substitui a definição inteira: os que você omitir são removidos. Índices não são afetados pelo `change()`; não precisa repeti-los, e `->unique()->change()` cria um índice novo.
::

O `down()` deve desfazer exatamente o `up()`, na ordem inversa, para que `migrate:rollback` funcione.

### Índices

Um índice é uma estrutura auxiliar que permite ao banco achar linhas sem ler a tabela inteira. Toda coluna usada com frequência em `where`, `order by` ou `join` é candidata. Índices podem ser criados de duas formas: encadeados na coluna (`->index()`), quando envolvem uma coluna só, ou como chamada separada na tabela (`$table->index([...])`), quando envolvem várias.

```php [database/migrations/2026_11_09_120000_create_pedidos_table.php]
Schema::create('pedidos', function (Blueprint $table) {
    $table->id();
    $table->string('numero')->unique();                   // índice único de uma coluna
    $table->string('status')->index();                    // índice comum de uma coluna
    $table->foreignId('cliente_id');
    $table->foreignId('loja_id');
    $table->string('sku');
    $table->text('descricao');
    $table->timestamps();

    $table->index(['cliente_id', 'created_at']);          // composto: a ordem das colunas importa
    $table->unique(['loja_id', 'sku']);                   // a combinação é única
    $table->fullText('descricao')->language('portuguese');
    $table->index('status', 'pedidos_status_idx');        // nome escolhido
});
```

| Método | Cria | Uso |
| --- | --- | --- |
| `index()` | Índice comum (B-tree) | Acelerar filtros e ordenação |
| `unique()` | Índice que também impede valores repetidos | E-mail, número do pedido, slug |
| `primary()` | Chave primária (única e não nula) | Chaves `uuid`/`ulid` ou compostas: `primary(['pedido_id', 'produto_id'])` |
| `fullText()` | Índice de busca por palavras | `whereFullText()` ([seção 18.10](#filtros-where-texto-wherelike-e-busca-full-text)) |
| `spatialIndex()` | Índice espacial | Colunas geométricas |
| `rawIndex('lower(email)', 'users_email_lower_idx')` | Índice sobre uma expressão | Buscas sem diferenciar maiúsculas |

**Índice composto e ordem das colunas**: `index(['cliente_id', 'created_at'])` atende consultas que filtram por `cliente_id`, e por `cliente_id` + `created_at`, mas **não** as que filtram só por `created_at`. Coloque primeiro a coluna que sempre aparece no filtro.

`unique()` × `index()`: o `unique` é um índice **e** uma regra; o banco recusa o `INSERT` duplicado mesmo que a validação da aplicação falhe (duas requisições simultâneas, por exemplo). Para garantir unicidade, use `unique()`, não só a regra de validação.

Para remover, passe o nome do índice ou o array de colunas (o Laravel monta o nome padrão `tabela_colunas_tipo`):

```php [database/migrations/2026_11_12_100000_drop_indices_from_pedidos_table.php]
Schema::table('pedidos', function (Blueprint $table) {
    $table->dropIndex(['cliente_id', 'created_at']);      // pelo array de colunas
    $table->dropIndex('pedidos_status_idx');              // pelo nome
    $table->dropUnique(['loja_id', 'sku']);
    $table->dropFullText(['descricao']);
    $table->dropPrimary();
    $table->renameIndex('pedidos_status_idx', 'pedidos_situacao_idx');
});
```

### Chaves estrangeiras

Uma chave estrangeira (FK) é uma regra no banco que diz: o valor desta coluna precisa existir na chave primária de outra tabela. Ela impede pedidos de um cliente que não existe e define o que acontece com os filhos quando o pai é apagado.

```php [database/migrations/2026_11_09_120000_create_pedidos_table.php]
Schema::create('pedidos', function (Blueprint $table) {
    $table->id();

    // forma curta: cria a coluna bigint e a FK para clientes.id
    $table->foreignId('cliente_id')->constrained();

    // tabela com nome diferente do deduzido
    $table->foreignId('autor_id')->nullable()->constrained('users')->nullOnDelete();

    // a partir do Model
    $table->foreignIdFor(Categoria::class)->constrained()->restrictOnDelete();

    // forma longa: coluna e FK declaradas separadas
    $table->unsignedBigInteger('loja_id');
    $table->foreign('loja_id')->references('id')->on('lojas')->cascadeOnDelete();
});
```

Como o `constrained()` deduz a tabela: tira o `_id` do nome da coluna e põe no plural em inglês. `cliente_id` vira `clientes`, `user_id` vira `users`. Quando o plural em inglês não funciona para o nome em português (`pais_id` viraria `pais`, não `paises`), informe a tabela: `constrained('paises')`.

`constrained()` × `foreign()->references()->on()`: fazem a mesma FK. A forma curta só funciona com colunas criadas por `foreignId`/`foreignIdFor`/`foreignUuid`/`foreignUlid`; a longa funciona com qualquer coluna e permite referenciar uma coluna que não é `id`.

O que acontece ao apagar (ou mudar a chave de) um registro pai:

| Método | Ao apagar o pai | Quando usar |
| --- | --- | --- |
| `cascadeOnDelete()` | Apaga os filhos junto | Filhos não existem sem o pai: itens do pedido |
| `nullOnDelete()` | Põe `null` na FK dos filhos (a coluna precisa ser `nullable`) | O filho continua fazendo sentido: post de um autor removido |
| `restrictOnDelete()` | Recusa apagar o pai enquanto houver filhos | Proteção: não apagar categoria com produtos |
| `noActionOnDelete()` | Parecido com `restrict`, mas checado no fim da transação | Raro; é o padrão quando nada é informado |
| `cascadeOnUpdate()` | Atualiza a FK dos filhos se a chave do pai mudar | Chaves naturais que podem mudar |

::note{type="pitfall" title="Cascade e eventos"}
O `cascadeOnDelete()` é executado pelo **banco**. O Eloquent não fica sabendo: eventos `deleting`/`deleted` e observers dos filhos não disparam, e o soft delete do pai não apaga os filhos (porque o pai não é removido de verdade).
::

Para remover a FK:

```php [database/migrations/2026_11_12_110000_drop_cliente_from_pedidos_table.php]
Schema::table('pedidos', function (Blueprint $table) {
    $table->dropForeign(['cliente_id']);                  // remove só a FK; a coluna fica
    $table->dropConstrainedForeignId('cliente_id');       // remove FK e coluna
});
```

Em testes e seeders, é possível desligar as FKs temporariamente com `Schema::disableForeignKeyConstraints()` e `Schema::enableForeignKeyConstraints()`, ou `Schema::withoutForeignKeyConstraints(fn () => ...)`.

### Migrations seguras em produção

- Nunca edite uma migration que já rodou em produção; crie outra.
- Coluna nova em tabela com dados: `nullable()` ou `default()`, senão o `ALTER` falha.
- Renomear ou remover coluna em uso exige etapas: publique o código que não usa mais a coluna, depois rode a migration que a remove.
- Índice em tabela grande no PostgreSQL trava escritas. Crie com `CONCURRENTLY`, fora de transação:

```php [database/migrations/2026_11_15_080000_add_status_index_to_pedidos_table.php]
return new class extends Migration
{
    public $withinTransaction = false;

    public function up(): void
    {
        DB::statement('CREATE INDEX CONCURRENTLY pedidos_status_idx ON pedidos (status)');
    }
};
```
