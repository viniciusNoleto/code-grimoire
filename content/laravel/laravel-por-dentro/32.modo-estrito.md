Por padrão, o Eloquent é tolerante: ignora campos não permitidos, carrega relacionamentos sob demanda e devolve `null` para atributos inexistentes. O modo estrito transforma esses silêncios em erros, o que ajuda muito quem está aprendendo.

### Ligar tudo de uma vez: `shouldBeStrict()`

No `AppServiceProvider::boot()`:

```php
use Illuminate\Database\Eloquent\Model;

Model::shouldBeStrict(! app()->isProduction());
```

Equivale a ligar as três proteções abaixo.

### As três proteções

| Método | Lança erro quando | Exceção |
| --- | --- | --- |
| `Model::preventLazyLoading(bool $value = true)` | Um relacionamento é acessado sem ter sido carregado com `with`/`load` | `LazyLoadingViolationException` |
| `Model::preventSilentlyDiscardingAttributes(bool $value = true)` | `create`/`fill`/`update` recebe um campo fora do `$fillable` | `MassAssignmentException` |
| `Model::preventAccessingMissingAttributes(bool $value = true)` | Você lê um atributo que não foi selecionado ou não existe (`$user->nmoe`) | `MissingAttributeException` |

```php
// Sem modo estrito: o campo 'role' é ignorado em silêncio
User::create(['nome' => 'Ana', 'role' => 'admin']);

// Com preventSilentlyDiscardingAttributes: MassAssignmentException
```

`preventAccessingMissingAttributes` também pega o caso de `User::select('id')->first()->email`, que normalmente devolveria `null` sem aviso.

Cada uma tem um handler para registrar em vez de lançar:

```php
Model::handleLazyLoadingViolationUsing(fn ($model, $relation) => Log::warning(...));
Model::handleDiscardedAttributeViolationUsing(fn ($model, $keys) => Log::warning(...));
Model::handleMissingAttributeViolationUsing(fn ($model, $key) => Log::warning(...));
```

### `unguard()` e `reguard()`

Desligam a proteção de mass assignment para **todos** os Models. Usado em seeders.

```php
Model::unguard();
User::create([...]);   // aceita qualquer campo
Model::reguard();

Model::unguarded(function () {   // só dentro da Closure
    User::create([...]);
});

Model::isUnguarded();   // bool
```

### Mass assignment: resumo de quando cada proteção vale

| Operação | Respeita `$fillable`? |
| --- | --- |
| `create`, `fill`, `update` (instância), `firstOrCreate`, `updateOrCreate`, `new Model([...])`, relação `->create()` | Sim |
| `forceFill`, `forceCreate`, atribuição direta (`$m->campo = x`) | Não |
| `insert`, `upsert`, update por query | Não (não usam o Model) |

::note{type="pitfall" title="Segurança"}
Nunca passe `$request->all()` direto para `create`/`update`. Use `$request->validated()` (Form Request) ou `$request->only([...])`.
::
