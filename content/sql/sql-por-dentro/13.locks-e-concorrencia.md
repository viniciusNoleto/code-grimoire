Duas transações que querem a mesma coisa ao mesmo tempo disputam um **lock**. Há locks de linha (quem altera o quê) e de tabela (quem pode mexer na estrutura), e a maioria dos incidentes de produção com banco travado vem de entender mal o segundo tipo.

### Locks de linha

```sql [row-locks.sql]
BEGIN;
SELECT saldo FROM contas WHERE id = 1 FOR UPDATE;   -- trava a linha até o fim da transação
-- outra sessão que fizer UPDATE ou FOR UPDATE nessa linha espera aqui
UPDATE contas SET saldo = 90 WHERE id = 1;
COMMIT;

-- Variações:
-- FOR NO KEY UPDATE  → como FOR UPDATE, mas não bloqueia inserts de FKs que apontam para ela
-- FOR SHARE          → impede alterações, permite outros FOR SHARE
-- NOWAIT             → erro imediato em vez de esperar
-- SKIP LOCKED        → pula linhas travadas (fila de jobs)
```

### Fila de jobs com SKIP LOCKED

```sql [fila.sql]
-- Vários workers pegam tarefas diferentes sem disputar a mesma linha
WITH proximo AS (
  SELECT id FROM jobs
  WHERE status = 'pendente' AND executar_em <= now()
  ORDER BY executar_em
  LIMIT 10
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs SET status = 'processando', iniciado_em = now()
FROM proximo WHERE jobs.id = proximo.id
RETURNING jobs.*;
```

### Os oito modos de lock de tabela

Todo comando pega um lock na tabela que toca. Os nomes confundem ("ROW EXCLUSIVE" é um lock de *tabela*, pego por UPDATE), mas o que importa é a matriz: dois modos conflitam ou não. Locks que não conflitam convivem; o segundo pedido de um modo conflitante entra na fila e espera.

| Modo | Pego por | Conflita com |
| --- | --- | --- |
| `ACCESS SHARE` | `SELECT` | só `ACCESS EXCLUSIVE` |
| `ROW SHARE` | `SELECT … FOR UPDATE / FOR SHARE` | `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `ROW EXCLUSIVE` | `INSERT`, `UPDATE`, `DELETE`, `MERGE` | `SHARE` e acima |
| `SHARE UPDATE EXCLUSIVE` | `VACUUM`, `ANALYZE`, `CREATE INDEX CONCURRENTLY`, `VALIDATE CONSTRAINT`, `DETACH PARTITION CONCURRENTLY` | ele mesmo e acima (dois VACUUMs na mesma tabela não rodam juntos) |
| `SHARE` | `CREATE INDEX` (sem CONCURRENTLY) | `ROW EXCLUSIVE` e acima, exceto ele mesmo: **bloqueia escritas** |
| `SHARE ROW EXCLUSIVE` | `CREATE TRIGGER`, `ADD FOREIGN KEY` (nas duas tabelas) | `ROW EXCLUSIVE` e acima, inclusive ele mesmo |
| `EXCLUSIVE` | `REFRESH MATERIALIZED VIEW CONCURRENTLY` | tudo, exceto `ACCESS SHARE`: só leituras passam |
| `ACCESS EXCLUSIVE` | `DROP`, `TRUNCATE`, `VACUUM FULL`, `CLUSTER`, `REINDEX`, `REFRESH MATERIALIZED VIEW`, a maioria dos `ALTER TABLE` (`ADD COLUMN`, `ALTER TYPE`, `DROP COLUMN`) | tudo, inclusive `SELECT` |

### A fila de DDL

Toda instrução pega um lock de tabela; quase todos são compatíveis entre si. O problema é o DDL: `ALTER TABLE` pede `ACCESS EXCLUSIVE`, que conflita até com `SELECT`. Se uma consulta longa estiver rodando, o ALTER espera, e **todas as consultas novas entram na fila atrás dele**: a aplicação para. Em migrações, defina um limite:

```sql [lock-timeout.sql]
SET lock_timeout = '3s';          -- desiste se não conseguir o lock rápido (tente de novo depois)
SET statement_timeout = '30s';
ALTER TABLE pedidos ADD COLUMN origem text;

-- Ver quem bloqueia quem
SELECT pid, pg_blocking_pids(pid) AS bloqueado_por, state, wait_event_type, query
FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

### Deadlocks, advisory locks e lock otimista

- **Deadlock**: A trava a linha 1 e espera a 2; B trava a 2 e espera a 1. O Postgres detecta (após `deadlock_timeout`) e aborta uma delas. Evite travando sempre na mesma ordem (por id).
- **Advisory locks** são locks com significado definido pela aplicação: `SELECT pg_try_advisory_lock(42)` garante que só um processo rode um cron, por exemplo. `pg_advisory_xact_lock` solta sozinho no fim da transação.
- **Lock otimista**: uma coluna `versao` e `UPDATE … SET versao = versao + 1 WHERE id = $1 AND versao = $2`. Se 0 linhas foram afetadas, alguém alterou antes; avise o usuário. Bom para edições demoradas em formulários, sem segurar transação aberta.
