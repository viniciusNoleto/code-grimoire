`LIKE '%termo%'` procura uma sequência exata de caracteres. Não encontra "índice" quando o texto diz "índices", não ignora "de", "a", "o", não sabe que o termo no título vale mais que no rodapé e, sem índice adequado, lê a tabela inteira. A busca textual do Postgres resolve isso transformando texto em **lexemas**: formas normalizadas das palavras.

### Como funciona: de texto a tsvector

1. **Parser**: quebra o texto em tokens e classifica cada um (palavra, número, e-mail, URL, hífen…).
2. **Dicionários**, definidos pela *configuração de busca* (`'portuguese'`, `'english'`, `'simple'`): descartam *stopwords* ("os", "de", "para") e reduzem cada palavra ao radical com um *stemmer* Snowball ("consultas", "consulta", "consultar" viram algo como `consult`).
3. **tsvector**: o resultado é a lista de lexemas com as **posições** em que aparecem, e opcionalmente um **peso** (A, B, C, D).

```sql [tsvector.sql]
SELECT to_tsvector('portuguese', 'Os índices aceleram as consultas; consultar sem índice é lento');
-- algo como: 'acel':3 'consult':5,6 'lent':10 'índic':2,8
--   "os", "as", "sem", "é" sumiram (stopwords); "consultas" e "consultar" viraram o mesmo lexema; posições preservadas

SELECT to_tsvector('simple', 'Os índices aceleram');   -- 'simple' só baixa maiúsculas: 'aceleram':3 'os':1 'índices':2
```

### Consultas: tsquery

A busca é um `tsquery`, também normalizado pela mesma configuração, comparado com o operador `@@`.

| Função | Entrada | Vira | Use quando |
| --- | --- | --- | --- |
| `websearch_to_tsquery` | `índice "busca textual" -mysql` | `'índic' & 'busc' <-> 'textual' & !'mysql'` | Texto digitado pelo usuário: aceita aspas, `-` e `or`, e nunca dá erro de sintaxe. |
| `plainto_tsquery` | `índices rápidos` | `'índic' & 'rápid'` | Todas as palavras, sem operadores. |
| `phraseto_tsquery` | `busca textual` | `'busc' <-> 'textual'` | Frase exata (em sequência). |
| `to_tsquery` | `postgr:* & (índic \| index)` | como escrito | Consultas montadas por você; erra com sintaxe inválida. `:*` = prefixo (autocompletar). |

### Montando de verdade: coluna, pesos, índice e ranking

```sql [artigos-busca.sql]
-- 1. Coluna gerada com pesos: título vale mais (A) que o resumo (B) e o corpo (C)
ALTER TABLE artigos ADD COLUMN busca tsvector GENERATED ALWAYS AS (
  setweight(to_tsvector('portuguese', coalesce(titulo, '')), 'A') ||
  setweight(to_tsvector('portuguese', coalesce(resumo, '')), 'B') ||
  setweight(to_tsvector('portuguese', coalesce(corpo,  '')), 'C')
) STORED;

-- 2. Índice GIN: "quais documentos contêm este lexema?"
CREATE INDEX artigos_busca_gin ON artigos USING gin (busca);

-- 3. Consulta com ranking e trecho destacado
WITH q AS (SELECT websearch_to_tsquery('portuguese', $1) AS q),
encontrados AS (
  SELECT a.id, a.titulo, a.corpo, ts_rank_cd(a.busca, q.q, 32) AS relevancia, q.q
  FROM artigos a, q
  WHERE a.busca @@ q.q
  ORDER BY relevancia DESC
  LIMIT 10
)
SELECT id, titulo, relevancia,
       ts_headline('portuguese', corpo, q, 'MaxFragments=2, MaxWords=20, MinWords=8') AS trecho
FROM encontrados;
```

- **Coluna gerada `STORED` vs índice de expressão** (`CREATE INDEX … USING gin (to_tsvector('portuguese', corpo))`): o índice de expressão economiza espaço, mas toda consulta precisa repetir exatamente a mesma expressão, e o ranking recalcula o tsvector de cada linha. A coluna gerada é mais simples de usar e mais rápida para ranquear.
- **`ts_rank` vs `ts_rank_cd`**: o primeiro pondera pela frequência dos termos; o segundo (*cover density*) também considera a proximidade entre eles. O último argumento normaliza pelo tamanho do documento (32 = escala para 0 a 1), evitando que textos longos ganhem só por serem longos.
- **`ts_headline` é cara**: ela reprocessa o texto original. Aplique só nas linhas finais, depois do `LIMIT`, como no exemplo.
- **GIN vs GiST para tsvector**: GIN é bem mais rápido na busca e o padrão; GiST é menor e mais barato de atualizar, mas gera falsos positivos rechecados. Prefira GIN.

### Acentos: configuração própria com unaccent

O stemmer português mantém acentos: quem busca "indice" não acha "índice". A solução é uma configuração que remove acentos antes de reduzir as palavras:

```sql [config-pt-sem-acento.sql]
CREATE EXTENSION IF NOT EXISTS unaccent;
CREATE TEXT SEARCH CONFIGURATION pt_sem_acento (COPY = portuguese);
ALTER TEXT SEARCH CONFIGURATION pt_sem_acento
  ALTER MAPPING FOR hword, hword_part, word WITH unaccent, portuguese_stem;

SELECT to_tsvector('pt_sem_acento', 'Índices e consultas');  -- lexemas sem acento
-- Use a mesma configuração na coluna gerada e nas consultas
```

### Vantagens, limites e quando usar outra coisa

| Vantagens | Limitações |
| --- | --- |
| Já está no banco: transacional, sem sincronizar outro sistema, junta com filtros e JOINs comuns. Stemming, stopwords, frases, prefixo, pesos e ranking. Rápida com GIN até milhões de documentos. | Não tolera erros de digitação ("indcie"): combine com trigramas. O ranking nativo não é BM25 e não usa estatísticas da coleção inteira; a relevância fica abaixo de motores dedicados. Sem facetas, sinônimos ricos ou "você quis dizer" prontos. Ordenar por relevância exige calcular o rank de todas as linhas que casam (consultas muito genéricas ficam lentas). Uma configuração por documento: conteúdo multilíngue exige uma coluna de idioma. |

**Use a busca nativa** para busca em produtos, artigos, tickets e documentos internos de um sistema. **Considere um motor dedicado** (Elasticsearch, OpenSearch, Meilisearch, Typesense) ou extensões como ParadeDB (BM25 no Postgres) quando relevância é o produto principal, há facetas complexas ou volume de dezenas de milhões de documentos com busca muito genérica.
