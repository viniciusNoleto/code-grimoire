Um banco que funciona no desenvolvimento precisa de mais coisas para aguentar produção: segurança contra injeção e acesso indevido, conexões controladas, limpeza contínua das versões mortas e um plano de backup.

### SQL injection: sempre parâmetros

```js [injection.js]
// ❌ concatenação: email = "x' OR '1'='1" devolve todos os usuários
db.query(`SELECT * FROM usuarios WHERE email = '${email}'`);

// ✅ parâmetro: o valor nunca é interpretado como SQL
db.query('SELECT * FROM usuarios WHERE email = $1', [email]);

// Nomes de tabela/coluna não podem ser parâmetros: use uma lista permitida no código
const ordem = { nome: 'nome', data: 'criado_em' }[req.query.ordem] ?? 'criado_em';
// No PL/pgSQL dinâmico: format('SELECT * FROM %I WHERE id = %L', tabela, id)
```

### Papéis, privilégios e Row-Level Security

```sql [seguranca.sql]
CREATE ROLE app_leitura NOLOGIN;
GRANT USAGE ON SCHEMA public TO app_leitura;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_leitura;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO app_leitura;

CREATE ROLE api LOGIN PASSWORD '...' IN ROLE app_leitura;   -- a aplicação nunca usa superusuário
GRANT INSERT, UPDATE ON pedidos TO api;

-- RLS: cada inquilino só vê as próprias linhas, mesmo que a aplicação esqueça o WHERE
ALTER TABLE pedidos ENABLE ROW LEVEL SECURITY;
CREATE POLICY por_inquilino ON pedidos
  USING (inquilino_id = current_setting('app.inquilino_id')::bigint);
-- a aplicação, por transação: SET LOCAL app.inquilino_id = '42';
```

### Conexões e pooling

Cada conexão no Postgres é um **processo** do sistema operacional, com memória própria. Milhares de conexões diretas (comum com serverless ou muitas réplicas da aplicação) derrubam o servidor. Use um pool: o da própria aplicação e, em escala, o **PgBouncer** em modo *transaction* (que não suporta recursos de sessão como `SET` sem `LOCAL`, advisory locks de sessão ou `LISTEN`).

### VACUUM e autovacuum por dentro

Por causa do MVCC, cada UPDATE e DELETE deixa uma versão morta para trás. O **VACUUM** faz quatro coisas: (1) marca o espaço das versões mortas como reutilizável na própria tabela (ele não devolve espaço ao sistema operacional, a tabela não encolhe); (2) remove as entradas de índice que apontavam para elas; (3) atualiza o *visibility map*, que permite index-only scans; (4) **congela** linhas antigas, como explicado abaixo. O **ANALYZE** atualiza as estatísticas do planejador.

O autovacuum dispara numa tabela quando as linhas mortas passam de um limite:

::formula{expr="limite = autovacuum_vacuum_threshold (50) + autovacuum_vacuum_scale_factor (0,2) × linhas"}
::

Numa tabela de 100 milhões de linhas, isso significa esperar **20 milhões** de linhas mortas antes de agir: tarde demais. Para tabelas grandes e muito atualizadas, ajuste por tabela:

```sql [autovacuum.sql]
ALTER TABLE eventos SET (
  autovacuum_vacuum_scale_factor = 0.01,     -- 1% em vez de 20%
  autovacuum_vacuum_threshold = 10000,
  autovacuum_analyze_scale_factor = 0.02
);
-- Tabelas só de inserção também precisam de VACUUM (visibility map, freeze):
-- autovacuum_vacuum_insert_scale_factor (PG 13) cuida disso.
-- Global: autovacuum_max_workers (PG 18 permite ajustar sem restart), autovacuum_vacuum_cost_limit (velocidade).
```

### Wraparound e freeze

IDs de transação têm 32 bits (cerca de 4 bilhões) e são comparados de forma circular: metade do espaço é "passado", metade "futuro". Uma linha muito antiga que não for marcada como congelada (*frozen*, visível para todos para sempre) pareceria vir do futuro depois de 2 bilhões de transações, e sumiria. O VACUUM congela linhas antigas para evitar isso. Se ele não acompanhar, o Postgres primeiro roda VACUUMs agressivos (*to prevent wraparound*) e, no limite, para de aceitar escritas.

```sql [wraparound.sql]
-- Quão perto cada database está (o limite de proteção é ~2 bilhões; alerte bem antes, ex.: 500 milhões)
SELECT datname, age(datfrozenxid) AS idade_xid FROM pg_database ORDER BY 2 DESC;

-- Tabelas mais antigas sem freeze
SELECT relname, age(relfrozenxid) AS idade_xid, pg_size_pretty(pg_total_relation_size(oid))
FROM pg_class WHERE relkind = 'r' ORDER BY age(relfrozenxid) DESC LIMIT 10;
```

### O que impede o VACUUM de limpar

O VACUUM só remove versões que **nenhuma transação ainda pode ver**. Ele calcula isso pelo `xmin` mais antigo do sistema. Quatro coisas seguram esse horizonte:

1. Transações longas ou `idle in transaction` (veja `backend_xmin` em `pg_stat_activity`).
2. Réplicas com `hot_standby_feedback = on` rodando consultas longas.
3. Slots de replicação abandonados (`xmin` e `catalog_xmin` em `pg_replication_slots`).
4. Transações preparadas esquecidas (`pg_prepared_xacts`).

Sintoma: `n_dead_tup` crescendo mesmo com o autovacuum rodando, e o log dizendo que tuplas "are dead but not yet removable".

### Recuperar espaço de verdade

- **`VACUUM FULL`** reescreve a tabela compactada, mas com `ACCESS EXCLUSIVE` (nada lê nem escreve) e espaço extra do tamanho da tabela.
- **`pg_repack`** (extensão) faz o mesmo com locks curtos; o PG 19 traz `REPACK (CONCURRENTLY)` nativo.
- Para medir bloat com precisão, a extensão `pgstattuple` lê a tabela e informa espaço livre e morto.

### Backup, replicação e alta disponibilidade

- **`pg_dump` / `pg_restore`**: backup lógico de um database. Bom para migrações e bancos pequenos; lento para restaurar bancos grandes.
- **Backup físico + WAL (PITR)**: cópia dos arquivos (`pg_basebackup`, pgBackRest, Barman) mais o arquivamento contínuo do WAL permite restaurar para qualquer instante. O PG 17 trouxe backups incrementais.
- **Replicação por streaming**: réplicas só leitura que aplicam o WAL do primário. Leituras na réplica podem estar atrasadas (*replication lag*).
- **Replicação lógica**: publica mudanças de tabelas selecionadas (`CREATE PUBLICATION` / `SUBSCRIPTION`), útil para upgrades sem downtime e para alimentar outros sistemas.

### LISTEN / NOTIFY

```sql [notify.sql]
LISTEN pedidos_novos;                                -- sessão que escuta (a conexão precisa ficar aberta)
NOTIFY pedidos_novos, '{"id": 1042}';                -- qualquer sessão envia; entregue no COMMIT
SELECT pg_notify('pedidos_novos', json_build_object('id', NEW.id)::text);  -- dentro de um trigger
-- Mensagens não persistem: quem não estava escutando perde. Para garantias, use uma tabela de outbox.
```

### Extensões que valem conhecer

| Extensão | Para quê |
| --- | --- |
| `pg_stat_statements` | Estatísticas de todas as consultas. |
| `pg_trgm`, `unaccent` | Busca aproximada; remover acentos. |
| `btree_gist` | Igualdade em índices GiST (necessário para `EXCLUDE` com `=`). |
| `pgvector` | Vetores e busca por similaridade (embeddings, IA). |
| `PostGIS` | Dados geográficos. |
| `pg_partman`, `pg_cron` | Gestão de partições; agendamento de jobs no banco. |
| `postgres_fdw` | Consultar tabelas de outro servidor Postgres como se fossem locais. |
