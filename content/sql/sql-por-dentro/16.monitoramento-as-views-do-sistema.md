O Postgres expõe o próprio estado como tabelas que você consulta com SQL. Há dois grupos:

- **Estatísticas dinâmicas** (`pg_stat_*`, `pg_statio_*`, `pg_locks`): o que está acontecendo agora e contadores acumulados desde o último reset.
- **Catálogo** (`pg_class`, `pg_index`, `pg_settings`…): a definição dos objetos e configurações. O `information_schema` é a versão padrão SQL, portátil mas mais lenta e incompleta; o `pg_catalog` é a fonte completa. Para descobrir como o psql obtém algo, rode `\set ECHO_HIDDEN on` e use `\d tabela`: ele mostra a consulta.

Contadores `pg_stat_*` são acumulativos. Um número isolado diz pouco; o que importa é a **variação** entre duas leituras, ou a proporção entre colunas. Quando foram zerados aparece em `stats_reset`.

### pg_stat_activity: o que está rodando agora

Uma linha por processo do servidor: cada conexão de cliente e os processos internos (autovacuum, checkpointer, walsender…).

| Coluna | O que diz |
| --- | --- |
| `pid` | Processo. É o identificador usado para cancelar e para cruzar com `pg_locks`. |
| `usename`, `datname`, `application_name`, `client_addr` | Quem e de onde. Configure `application_name` na string de conexão de cada serviço para saber qual deles é o culpado. |
| `state` | `active` (executando), `idle` (esperando o cliente), `idle in transaction` (transação aberta, sem fazer nada: segura locks e impede o VACUUM), `idle in transaction (aborted)` (deu erro e o cliente não fez ROLLBACK). |
| `xact_start`, `query_start`, `state_change` | Início da transação, da consulta atual e da última troca de estado. `now() - xact_start` é a idade da transação. |
| `wait_event_type`, `wait_event` | Pelo que o processo espera. `Lock` = lock de outro processo; `IO` = disco; `LWLock` = estruturas internas (contenção); `Client` = esperando a aplicação ler ou enviar; nulo com `active` = usando CPU. |
| `backend_xmin` | O snapshot mais antigo que esse processo ainda enxerga. É ele que segura o VACUUM. |
| `query`, `query_id` | Texto da consulta atual ou da última (se `idle`); `query_id` cruza com `pg_stat_statements` (exige `compute_query_id`). |
| `backend_type` | `client backend` para conexões; os demais são processos internos. |

```sql [atividade.sql]
-- Consultas ativas, da mais antiga para a mais nova
SELECT pid, usename, application_name, state, wait_event_type, wait_event,
       now() - query_start AS duracao, left(query, 100) AS consulta
FROM pg_stat_activity
WHERE backend_type = 'client backend' AND state <> 'idle' AND pid <> pg_backend_pid()
ORDER BY query_start;

-- Transações abertas há mais de 5 minutos (inclusive paradas)
SELECT pid, usename, application_name, state, now() - xact_start AS idade_transacao, left(query, 80)
FROM pg_stat_activity
WHERE xact_start < now() - interval '5 minutes'
ORDER BY xact_start;

-- Conexões por aplicação e estado (detecta vazamento de conexões)
SELECT application_name, state, count(*) FROM pg_stat_activity
WHERE backend_type = 'client backend' GROUP BY 1, 2 ORDER BY 3 DESC;
```

### Cancelar e encerrar

```sql [cancelar.sql]
SELECT pg_cancel_backend(12345);      -- cancela a consulta atual; a conexão continua (como Ctrl+C)
SELECT pg_terminate_backend(12345);   -- derruba a conexão; a transação sofre ROLLBACK

-- Limites que evitam precisar fazer isso à mão (por role ou database: ALTER ROLE api SET ...)
SET statement_timeout = '30s';                    -- consulta mais longa que isso é cancelada
SET lock_timeout = '5s';                          -- desiste de esperar lock
SET idle_in_transaction_session_timeout = '60s';  -- derruba transação esquecida aberta
SET transaction_timeout = '5min';                 -- PG 17: limite para a transação inteira
```

### pg_locks: quem segura e quem espera

Uma linha por lock pedido ou concedido. `granted = false` significa que o processo está na fila. As colunas que importam: `locktype` (`relation` = tabela ou índice, `tuple` = linha, `transactionid` = esperando outra transação terminar, `advisory`), `relation` (o OID; converta com `::regclass`), `mode` (veja a matriz no [capítulo 13](#locks-e-concorrencia)), `pid` e `waitstart` (PG 14: desde quando espera).

Um detalhe importante: locks de **linha** não aparecem um por linha (seriam milhões). Quem espera por uma linha aparece esperando o `transactionid` de quem a modificou. Por isso a forma mais prática de achar bloqueios é a função `pg_blocking_pids(pid)`, que já resolve isso.

```sql [bloqueios.sql]
-- Quem está bloqueado, há quanto tempo, e por quem
SELECT bloqueado.pid                       AS pid_bloqueado,
       now() - bloqueado.query_start       AS esperando_ha,
       left(bloqueado.query, 60)           AS consulta_bloqueada,
       bloqueador.pid                      AS pid_bloqueador,
       bloqueador.state                    AS estado_bloqueador,
       now() - bloqueador.xact_start       AS idade_tx_bloqueadora,
       left(bloqueador.query, 60)          AS consulta_bloqueadora
FROM pg_stat_activity bloqueado
CROSS JOIN LATERAL unnest(pg_blocking_pids(bloqueado.pid)) AS b(pid)
JOIN pg_stat_activity bloqueador ON bloqueador.pid = b.pid
ORDER BY esperando_ha DESC;

-- A raiz da fila: processos que bloqueiam outros mas não esperam ninguém
SELECT pid, state, now() - xact_start AS idade, left(query, 80)
FROM pg_stat_activity a
WHERE pid IN (SELECT unnest(pg_blocking_pids(pid)) FROM pg_stat_activity)
  AND cardinality(pg_blocking_pids(pid)) = 0;

-- Locks de tabela em detalhe, com nome legível
SELECT l.pid, l.relation::regclass AS objeto, l.mode, l.granted, l.waitstart
FROM pg_locks l WHERE l.locktype = 'relation' AND l.database = (SELECT oid FROM pg_database WHERE datname = current_database())
ORDER BY l.granted, l.waitstart;
```

::note{type="note" title="Diagnóstico típico"}
Dezenas de consultas esperando com `wait_event_type = Lock`, e a raiz é um processo `idle in transaction` há 40 minutos: alguém abriu uma transação num console, fez um UPDATE e foi almoçar, ou a aplicação não fecha transações em um caminho de erro. Encerrar a raiz destrava a fila; a correção definitiva é o `idle_in_transaction_session_timeout` e consertar o código.
::

### pg_stat_statements: onde o banco gasta tempo

Agrega todas as consultas executadas, normalizadas (literais viram `$1`, `$2`), com contadores. É a ferramenta mais importante para performance, porque mostra a **carga total**: uma consulta de 2 ms chamada 5 milhões de vezes pesa mais que uma de 3 s chamada 10 vezes.

```sql [statements.sql]
-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements' (exige restart); depois:
CREATE EXTENSION pg_stat_statements;

-- Top 10 por tempo total
SELECT queryid, calls,
       round(total_exec_time::numeric / 1000, 1)                          AS segundos_total,
       round(mean_exec_time::numeric, 2)                                  AS ms_media,
       round(stddev_exec_time::numeric, 2)                                AS ms_desvio,
       rows / nullif(calls, 0)                                            AS linhas_por_chamada,
       round(100.0 * shared_blks_hit / nullif(shared_blks_hit + shared_blks_read, 0), 1) AS pct_cache,
       temp_blks_written,
       left(query, 80)                                                    AS consulta
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

SELECT pg_stat_statements_reset();   -- zera para medir uma janela (ex.: antes e depois de um deploy)
```

- **`calls` altíssimo com `rows` = 1** é a assinatura de um N+1 na aplicação.
- **`stddev_exec_time` grande** em relação à média: a mesma consulta às vezes é rápida e às vezes lenta (cache frio, parâmetros com distribuição diferente, bloqueios).
- **`temp_blks_written` > 0**: ordenação ou hash não coube em `work_mem` e foi para disco.
- **`pct_cache` baixo**: a consulta lê muito do disco; talvez falte índice ou a tabela não caiba em memória.

### pg_stat_user_tables e pg_stat_user_indexes: saúde de cada tabela

| Coluna | Como interpretar |
| --- | --- |
| `seq_scan`, `seq_tup_read` | Leituras completas. Muitas numa tabela grande, com `seq_tup_read / seq_scan` alto, indicam índice faltando. |
| `idx_scan`, `last_idx_scan` (PG 16) | Uso de índices na tabela. |
| `n_tup_ins`, `n_tup_upd`, `n_tup_hot_upd`, `n_tup_del` | Volume de escrita. `hot_upd / upd` baixo em tabela muito atualizada: índices demais ou página sem espaço. |
| `n_live_tup`, `n_dead_tup` | Linhas vivas e mortas estimadas. Mortas crescendo sem parar: o autovacuum não está acompanhando ou algo segura o xmin. |
| `last_autovacuum`, `last_autoanalyze`, `autovacuum_count` | Quando o autovacuum passou. Nulo numa tabela ativa é sinal de problema. |

```sql [tabelas.sql]
-- Tabelas que mais leem por varredura completa
SELECT relname, seq_scan, seq_tup_read, idx_scan,
       seq_tup_read / nullif(seq_scan, 0) AS linhas_por_varredura,
       pg_size_pretty(pg_relation_size(relid)) AS tamanho
FROM pg_stat_user_tables
ORDER BY seq_tup_read DESC LIMIT 10;

-- Lixo acumulado e eficiência de HOT
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS pct_morto,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1)            AS pct_hot,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 10;

-- Índices nunca usados (candidatos a remoção; confira réplicas antes: as estatísticas são por servidor)
SELECT s.relname AS tabela, s.indexrelname AS indice, s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS tamanho
FROM pg_stat_user_indexes s JOIN pg_index i USING (indexrelid)
WHERE s.idx_scan = 0 AND NOT i.indisunique AND NOT i.indisprimary
ORDER BY pg_relation_size(s.indexrelid) DESC;
```

### Cache, database e I/O

```sql [cache.sql]
-- Proporção de leituras atendidas pelo shared_buffers (não conta o cache do sistema operacional)
SELECT datname,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS pct_cache,
       xact_commit, xact_rollback, deadlocks, temp_files,
       pg_size_pretty(temp_bytes) AS temp_total, stats_reset
FROM pg_stat_database WHERE datname = current_database();

-- Por tabela: pg_statio_user_tables (heap_blks_hit / heap_blks_read, idx_blks_hit / idx_blks_read)

-- PG 16: I/O por tipo de processo e contexto
SELECT backend_type, object, context, reads, writes, extends, hits, evictions
FROM pg_stat_io WHERE reads > 0 OR writes > 0 ORDER BY reads DESC;

-- PG 17: checkpoints (antes em pg_stat_bgwriter)
SELECT num_timed, num_requested, write_time, sync_time FROM pg_stat_checkpointer;
```

- **`pct_cache`** abaixo de ~99% em aplicações OLTP costuma indicar memória insuficiente ou consultas varrendo tabelas grandes.
- **`deadlocks` crescendo**: transações travando linhas em ordens diferentes.
- **`xact_rollback` alto** em relação a commits: erros frequentes na aplicação (ou retries de serialização).
- **`num_requested` maior que `num_timed`**: checkpoints forçados por volume de WAL; aumente `max_wal_size`.
- **Em `pg_stat_io`**, muitos `writes` feitos por `client backend` significam que as próprias conexões estão gravando páginas sujas para liberar espaço, em vez do bgwriter: `shared_buffers` pequeno ou bgwriter pouco agressivo.

### Operações longas: pg_stat_progress_*

```sql [progresso.sql]
-- VACUUM em andamento: fase e quanto falta
SELECT pid, relid::regclass AS tabela, phase,
       round(100.0 * heap_blks_scanned / nullif(heap_blks_total, 0), 1) AS pct_varrido,
       index_vacuum_count
FROM pg_stat_progress_vacuum;

-- CREATE INDEX (inclusive CONCURRENTLY)
SELECT pid, relid::regclass, index_relid::regclass, phase,
       round(100.0 * blocks_done / nullif(blocks_total, 0), 1) AS pct
FROM pg_stat_progress_create_index;

-- Também: pg_stat_progress_analyze, _cluster (CLUSTER e VACUUM FULL), _copy (PG 14), _basebackup
```

### Replicação

```sql [replicacao.sql]
-- No primário: cada réplica conectada e o atraso
SELECT application_name, client_addr, state, sync_state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS atraso_bytes,
       replay_lag
FROM pg_stat_replication;

-- Slots de replicação: o perigo silencioso
SELECT slot_name, slot_type, active, wal_status,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_retido
FROM pg_replication_slots;

-- Na réplica
SELECT now() - pg_last_xact_replay_timestamp() AS atraso_aproximado;
```

::note{type="pitfall" title="Slot inativo enche o disco"}
Um slot de replicação garante que o primário guarde todo WAL que o consumidor ainda não leu. Se o consumidor (uma réplica removida, uma ferramenta de CDC desligada) some, o slot fica `active = false` e o WAL cresce até lotar o disco e derrubar o banco. Monitore `wal_retido`, defina `max_slot_wal_keep_size` e remova slots órfãos com `pg_drop_replication_slot('nome')`.
::

### Tamanhos e configuração

```sql [tamanhos.sql]
-- Maiores tabelas, separando dados, índices e TOAST (valores grandes guardados à parte)
SELECT c.relname,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS total,
       pg_size_pretty(pg_relation_size(c.oid))       AS dados,
       pg_size_pretty(pg_indexes_size(c.oid))        AS indices,
       c.reltuples::bigint                           AS linhas_estimadas
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r' AND n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY pg_total_relation_size(c.oid) DESC LIMIT 15;

SELECT pg_size_pretty(pg_database_size(current_database()));

-- Configurações: valor, de onde veio e se precisa de restart
SELECT name, setting, unit, source, context, pending_restart
FROM pg_settings WHERE name IN ('shared_buffers', 'work_mem', 'max_connections', 'autovacuum_vacuum_scale_factor');
ALTER SYSTEM SET work_mem = '32MB';   -- grava em postgresql.auto.conf
SELECT pg_reload_conf();              -- aplica o que não exige restart (context = 'user' ou 'sighup')
```

### Logs que valem ligar

| Parâmetro | Efeito |
| --- | --- |
| `log_min_duration_statement = '500ms'` | Registra toda consulta mais lenta que isso, com o texto. |
| `log_lock_waits = on` | Registra quem esperou mais que `deadlock_timeout` por um lock, e por quem. |
| `log_autovacuum_min_duration = '10s'` | Mostra quais tabelas o autovacuum processa e quanto tempo leva. |
| `log_temp_files = 0` | Registra todo arquivo temporário (falta de `work_mem`). |
| `log_checkpoints = on` | Frequência e duração dos checkpoints (ligado por padrão desde o PG 15). |
| `auto_explain.log_min_duration` | Extensão: grava o plano de execução das consultas lentas. |
