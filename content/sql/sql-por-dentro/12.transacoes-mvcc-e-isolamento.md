Uma transação agrupa instruções que devem acontecer juntas ou não acontecer (**ACID**: atomicidade, consistência, isolamento, durabilidade). No Postgres, toda instrução solta já é uma transação; `BEGIN` abre uma explícita.

```sql [transacao.sql]
BEGIN;
UPDATE contas SET saldo = saldo - 100 WHERE id = 1;
UPDATE contas SET saldo = saldo + 100 WHERE id = 2;
SAVEPOINT antes_da_taxa;
INSERT INTO taxas (conta_id, valor) VALUES (1, 2.5);
ROLLBACK TO SAVEPOINT antes_da_taxa;   -- desfaz só a taxa
COMMIT;                                -- ou ROLLBACK para desfazer tudo

-- Erro dentro da transação: tudo após ele falha até ROLLBACK
-- ("current transaction is aborted, commands ignored until end of transaction block")
```

### MVCC: como leitores e escritores não se bloqueiam

O Postgres usa **controle de concorrência multiversão**. Um `UPDATE` não sobrescreve a linha: ele cria uma **nova versão** (tupla) e marca a antiga como expirada. Cada tupla guarda `xmin` (a transação que a criou) e `xmax` (a que a apagou ou substituiu). Cada consulta enxerga um **snapshot**: as versões confirmadas até aquele momento.

- **Leituras nunca esperam escritas** e escritas nunca esperam leituras. Só duas escritas na mesma linha disputam.
- **Versões antigas viram lixo** (*dead tuples*) quando nenhuma transação aberta precisa mais delas. O **VACUUM** (normalmente o autovacuum) recupera esse espaço.
- **Transações longas atrapalham todo mundo**: enquanto uma transação aberta há horas existir, o VACUUM não pode limpar versões que ela ainda poderia ver, e as tabelas incham (*bloat*). Cuidado com sessões "idle in transaction".

```sql [mvcc.sql]
SELECT xmin, xmax, ctid, * FROM contas WHERE id = 1;   -- colunas de sistema visíveis
UPDATE contas SET saldo = 90 WHERE id = 1;
SELECT xmin, xmax, ctid, * FROM contas WHERE id = 1;   -- xmin novo, ctid (posição física) mudou
```

### Níveis de isolamento

| Nível | Snapshot | O que pode acontecer |
| --- | --- | --- |
| `READ COMMITTED` (padrão) | Novo a cada instrução. | Leitura não repetível, phantom, lost update (no padrão ler-calcular-gravar), write skew. |
| `REPEATABLE READ` | Um só, desde a primeira instrução da transação. | Write skew. Conflitos de escrita geram erro `40001`. |
| `SERIALIZABLE` | Um só + detecção de dependências (SSI). | Nenhuma anomalia: o resultado equivale a alguma execução em série. Pode abortar com `40001`. |

`READ UNCOMMITTED` é aceito, mas se comporta como `READ COMMITTED`: o Postgres nunca mostra dados não confirmados.

::note{type="note" title="Na prática"}
Em `REPEATABLE READ` e `SERIALIZABLE`, a aplicação **precisa** tratar o erro `40001` (*serialization_failure*) repetindo a transação inteira. Muitos ORMs e drivers não fazem isso sozinhos. Para o problema mais comum, o lost update, a solução mais simples é fazer a conta no banco (`SET saldo = saldo - 10`) ou travar a linha com `SELECT … FOR UPDATE`.
::
