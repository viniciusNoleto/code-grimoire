O PostgreSQL vai além dos tipos escalares: um valor pode ser um intervalo inteiro, uma lista ou um conjunto fechado de rótulos, cada um com operadores e índices próprios.

### Ranges: um intervalo como um valor só

Um range guarda início e fim num único valor, com a informação de quais extremos são incluídos. Tipos embutidos: `int4range`, `int8range`, `numrange`, `daterange`, `tsrange`, `tstzrange`. A notação usa colchete para incluído e parêntese para excluído: `[2026-11-10, 2026-11-15)` inclui o dia 10 e exclui o 15.

- **Forma canônica**: ranges de tipos discretos (inteiros, datas) são normalizados para `[a, b)`. `int4range(1, 5, '[]')` vira `[1,6)`. Por isso comparar ranges de data funciona mesmo se cada um foi escrito de um jeito.
- **Sem limite**: `[2026-01-01,)` é "a partir de 1º de janeiro, sem fim" (vigência atual).
- **Vazio**: `'empty'` é um range válido que não contém nada.

| Operador | Significado | Exemplo | Resultado |
| --- | --- | --- | --- |
| `&&` | sobrepõe | `'[10,20)'::int4range && '[15,30)'` | `true` |
| `@>` | contém (range ou elemento) | `'[10,20)'::int4range @> 20` | `false` (20 está excluído) |
| `<@` | está contido | `'[12,14)'::int4range <@ '[10,20)'` | `true` |
| `-\|-` | adjacente (encosta sem sobrepor) | `'[10,20)'::int4range -\|- '[20,30)'` | `true` |
| `<<`, `>>` | totalmente à esquerda / direita | `'[1,5)'::int4range << '[5,9)'` | `true` |
| `*` | interseção | `'[10,20)'::int4range * '[15,30)'` | `[15,20)` |
| `+`, `-` | união / diferença (erro se o resultado não for contínuo; use multiranges) | `'[10,20)'::int4range + '[20,30)'` | `[10,30)` |

```sql [reservas.sql]
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE reservas (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sala_id int NOT NULL,
  periodo tstzrange NOT NULL CHECK (NOT isempty(periodo)),
  EXCLUDE USING gist (sala_id WITH =, periodo WITH &&)   -- o banco impede sobreposição, mesmo com concorrência
);

-- Salas livres entre 14h e 16h
SELECT s.id FROM salas s
WHERE NOT EXISTS (
  SELECT 1 FROM reservas r
  WHERE r.sala_id = s.id AND r.periodo && tstzrange('2026-11-10 14:00-04', '2026-11-10 16:00-04')
);

-- Funções: lower(), upper(), isempty(), lower_inc(), upper_inf(), range_merge()
SELECT upper(periodo) - lower(periodo) AS duracao FROM reservas;

-- Multiranges (PG 14): vários intervalos num valor; range_agg junta tudo
SELECT sala_id, range_agg(periodo) AS ocupacao FROM reservas GROUP BY sala_id;
-- {[14:00,15:00), [16:00,18:00)}
```

|   | Range | Duas colunas inicio / fim |
| --- | --- | --- |
| Impedir sobreposição | `EXCLUDE` resolve, correto sob concorrência | Só com trigger e lock, fácil de errar |
| Consulta "sobrepõe" | `a && b`, com índice GiST | `a.inicio < b.fim AND b.inicio < a.fim` (e cuidado com inclusivo/exclusivo) |
| Compatibilidade com ORMs | Pior: muitos não mapeiam o tipo | Melhor |
| Índices B-tree em "a partir de" | Usa GiST | B-tree simples em `inicio` |

Desde o PG 18, chaves com `WITHOUT OVERLAPS` e FKs com `PERIOD` trazem tabelas temporais (histórico de preços, vigências de contrato) para dentro de `PRIMARY KEY` e `REFERENCES`; o PG 19 adiciona `UPDATE/DELETE … FOR PORTION OF`.

### Arrays

Qualquer tipo pode virar array (`text[]`, `int[]`). Índices começam em **1**, e acessar fora do tamanho devolve `NULL`, não erro.

```sql [arrays.sql]
SELECT ARRAY['sql', 'postgres'] || 'indices';         -- {sql,postgres,indices}
SELECT (ARRAY[10, 20, 30])[2];                        -- 20
SELECT (ARRAY[10, 20, 30])[2:3];                      -- {20,30} (fatia)
SELECT cardinality(ARRAY[1, 2, 3]);                   -- 3  (array_length(a, 1) devolve NULL para array vazio)
SELECT array_position(ARRAY['a', 'b', 'c'], 'b');     -- 2
SELECT array_remove(ARRAY[1, 2, 1], 1);               -- {2}

-- Buscas: com GIN, @> e && usam índice; ANY não
CREATE INDEX posts_tags_gin ON posts USING gin (tags);
SELECT * FROM posts WHERE tags @> ARRAY['postgres'];          -- contém todas
SELECT * FROM posts WHERE tags && ARRAY['vue', 'react'];      -- contém alguma
SELECT * FROM posts WHERE 'sql' = ANY (tags);                 -- igual, mas sem índice GIN

-- Array → linhas (com a posição) e linhas → array
SELECT p.id, t.tag, t.pos FROM posts p, unnest(p.tags) WITH ORDINALITY AS t(tag, pos);
SELECT cliente_id, array_agg(id ORDER BY criado_em) FROM pedidos GROUP BY 1;

-- Passar listas da aplicação: um parâmetro só, plano reaproveitável
SELECT * FROM produtos WHERE id = ANY ($1::bigint[]);
```

|   | Array na coluna | Tabela de ligação (`post_tags`) |
| --- | --- | --- |
| Leitura do conjunto | Uma linha, sem JOIN | JOIN |
| Integridade (a tag existe?) | Não há FK para elementos de array | FK garante |
| Atributos na relação (quando foi marcada, por quem) | Impossível | Natural |
| Atualização | Reescreve a linha inteira | Insere ou apaga uma linha |
| Bom para | Listas curtas, sem identidade própria: tags livres, permissões, histórico de status | Relacionamentos de verdade, muitos-para-muitos |

### Enums

```sql [enums.sql]
CREATE TYPE status_pedido AS ENUM ('novo', 'pago', 'enviado', 'entregue', 'cancelado');
ALTER TABLE pedidos ALTER COLUMN status TYPE status_pedido USING status::status_pedido;

SELECT * FROM pedidos WHERE status > 'pago';        -- ordem é a da declaração: enviado, entregue, cancelado
ALTER TYPE status_pedido ADD VALUE 'devolvido' AFTER 'entregue';   -- adicionar é fácil
-- remover ou renomear para reorganizar: não há DROP VALUE; exige criar outro tipo e migrar a coluna
```

| Opção | Vantagens | Desvantagens |
| --- | --- | --- |
| `ENUM` | 4 bytes; valida; ordem própria; autodocumenta. | Não dá para remover valores; mudanças exigem migração de tipo; atributos extras (rótulo, cor) não cabem. |
| `text` + `CHECK (status IN (…))` | Simples; mudar é trocar a constraint (`NOT VALID` + `VALIDATE`). | Sem ordem semântica; texto repetido em cada linha. |
| Tabela de referência + FK | Valores gerenciáveis sem migração; atributos extras; desativar sem apagar. | Um JOIN para mostrar o rótulo. |

Regra prática: enum para conjuntos que quase nunca mudam e que o código trata caso a caso (estados de uma máquina de estados); tabela de referência quando usuários de negócio criam ou editam os valores.
