Particionar divide uma tabela lógica em várias tabelas físicas. Vale para tabelas muito grandes (centenas de milhões de linhas) com um critério natural de consulta e de descarte, como data. Os ganhos: **partition pruning** (consultas com filtro na chave só leem as partições relevantes) e **apagar dados antigos instantaneamente** com `DROP` ou `DETACH` de uma partição, em vez de um `DELETE` gigante.

```sql [particoes.sql]
CREATE TABLE eventos (
  id bigint GENERATED ALWAYS AS IDENTITY,
  criado_em timestamptz NOT NULL,
  tipo text NOT NULL,
  dados jsonb,
  PRIMARY KEY (id, criado_em)                -- PK e UNIQUE precisam incluir a chave de partição
) PARTITION BY RANGE (criado_em);

CREATE TABLE eventos_2026_11 PARTITION OF eventos FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
CREATE TABLE eventos_2026_12 PARTITION OF eventos FOR VALUES FROM ('2026-12-01') TO ('2027-01-01');
CREATE TABLE eventos_padrao PARTITION OF eventos DEFAULT;   -- recebe o que não couber

CREATE INDEX ON eventos (tipo, criado_em);  -- criado em todas as partições

ALTER TABLE eventos DETACH PARTITION eventos_2025_11 CONCURRENTLY;  -- tira sem travar
DROP TABLE eventos_2025_11;

-- Também: PARTITION BY LIST (pais) e PARTITION BY HASH (cliente_id)
-- PG 19: ALTER TABLE ... MERGE PARTITIONS / SPLIT PARTITION
```

Partições demais (milhares) pioram o planejamento. Automatize a criação das próximas com um job ou com a extensão `pg_partman`.
