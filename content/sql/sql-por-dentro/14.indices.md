Um índice é uma estrutura separada da tabela que permite achar linhas sem ler todas. A tabela em si (o *heap*) não tem ordem: linhas ficam onde houver espaço. Cada entrada de índice aponta para a posição física da linha (o `ctid`: página e posição na página). Ler pelo índice significa percorrer o índice e depois buscar cada linha no heap.

Todo índice tem custo: cada `INSERT` escreve em todos os índices da tabela, cada `UPDATE` que não for HOT (abaixo) também, e todos ocupam disco e memória de cache. Uma tabela com 12 índices escreve 13 vezes a cada inserção.

### B-tree: o padrão

**Como funciona.** Uma árvore balanceada de páginas de 8 KB. A raiz e as páginas internas guardam chaves separadoras; as folhas guardam as chaves ordenadas com os ponteiros para o heap e estão ligadas entre si numa lista. Achar um valor custa alguns saltos (uma árvore de 3 ou 4 níveis cobre centenas de milhões de linhas). Ler um intervalo é achar o início e seguir as folhas em ordem. Desde o PG 13, valores repetidos são **deduplicados** nas folhas, deixando índices em colunas pouco seletivas bem menores.

- **Atende**: `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`, `IN`, `IS NULL`, `ORDER BY` (nos dois sentidos), `LIKE 'abc%'` (se a collation for `C` ou o índice usar `text_pattern_ops`), `min`/`max`.
- **Não atende**: `LIKE '%abc'`, operadores de JSONB, arrays e ranges, busca textual.
- **Único tipo que garante `UNIQUE`** e chave primária.

### A ordem das colunas num índice composto

Um índice em `(cliente_id, status, criado_em)` é ordenado primeiro por cliente, depois por status dentro de cada cliente, depois por data. Ele se comporta como uma lista telefônica:

| Consulta | Usa bem o índice? | Por quê |
| --- | --- | --- |
| `WHERE cliente_id = 7` | sim | Prefixo do índice. |
| `WHERE cliente_id = 7 AND status = 'pago' ORDER BY criado_em DESC LIMIT 20` | sim, ideal | Igualdades nas duas primeiras colunas; a terceira já vem ordenada. Lê exatamente 20 entradas. |
| `WHERE cliente_id = 7 AND criado_em > now() - '7 days'` | parcialmente | Filtra pelo cliente; a data é verificada em cada entrada desse cliente (o status no meio "quebra" o intervalo). |
| `WHERE status = 'pago'` | só com skip scan (PG 18) | Sem a primeira coluna, precisaria pular para cada cliente. O PG 18 faz isso quando há poucos `cliente_id` distintos; senão, não compensa. |

Regra prática: **colunas comparadas por igualdade primeiro, depois a de intervalo ou de ordenação**. E prefira um índice composto bem pensado a vários índices de uma coluna (o Postgres consegue combiná-los com *bitmap AND*, mas é bem menos eficiente).

### Variações de B-tree

```sql [variacoes.sql]
-- Parcial: indexa só as linhas que você consulta. 2% da tabela = índice 50x menor.
CREATE INDEX pedidos_pendentes ON pedidos (criado_em) WHERE status = 'pendente';
--   só é usado quando a consulta tem WHERE status = 'pendente' (o planejador precisa provar a condição)

-- Expressão: indexa o resultado de uma função
CREATE INDEX clientes_email_lower ON clientes (lower(email));
--   usado por WHERE lower(email) = $1, não por WHERE email = $1

-- Covering (INCLUDE): colunas extras só nas folhas, para index-only scan
CREATE INDEX pedidos_cliente_cobre ON pedidos (cliente_id) INCLUDE (status, total);
--   SELECT status, total FROM pedidos WHERE cliente_id = 7 nem visita a tabela

-- Único parcial: um endereço principal por cliente, quantos secundários quiser
CREATE UNIQUE INDEX um_principal ON enderecos (cliente_id) WHERE principal;

-- LIKE 'prefixo%' em bancos com collation não-C
CREATE INDEX produtos_nome_prefixo ON produtos (nome text_pattern_ops);
```

### Index-only scan e o visibility map

Mesmo que o índice tenha todas as colunas da consulta, o Postgres precisa saber se cada linha é **visível** para a transação (MVCC), e essa informação mora no heap, não no índice. O atalho é o *visibility map*: um bit por página indicando "todas as linhas aqui são visíveis para todos". Para páginas marcadas, o index-only scan pula o heap. O VACUUM é quem marca as páginas, então tabelas com muitas escritas e VACUUM atrasado mostram `Heap Fetches` altos no EXPLAIN e perdem o benefício.

### HOT updates: por que menos índices deixam UPDATE mais rápido

Um `UPDATE` cria uma nova versão da linha. Se nenhuma coluna indexada mudou **e** há espaço livre na mesma página, o Postgres faz um **HOT update** (*heap-only tuple*): a nova versão fica na mesma página, encadeada à antiga, e **nenhum índice é tocado**. Se mudou uma coluna indexada, ou a página está cheia, todos os índices recebem uma entrada nova.

- Indexar uma coluna atualizada com frequência (`atualizado_em`, `contador_visitas`) desliga o HOT para todos os updates dela.
- `ALTER TABLE contadores SET (fillfactor = 80)` deixa 20% de cada página livre para versões HOT, em tabelas muito atualizadas.
- Acompanhe em `pg_stat_user_tables`: `n_tup_hot_upd` sobre `n_tup_upd` ([capítulo 16](#monitoramento-as-views-do-sistema)).

### Os outros tipos, por dentro

| Tipo | Como funciona | Vantagens | Desvantagens | Use para |
| --- | --- | --- | --- | --- |
| **GIN** | Índice invertido: para cada *elemento* (chave de JSONB, item de array, palavra, trigrama), uma lista ordenada das linhas que o contêm. Como o índice remissivo de um livro. | Muito rápido para "contém X", "contém X e Y". Listas comprimidas. | Escrita cara: uma linha gera muitas entradas. Com `fastupdate` (padrão), entradas novas vão para uma lista pendente que o VACUUM incorpora; leituras ficam mais lentas até lá. Não ordena. | `jsonb` (`@>`, `?`), arrays (`@>`, `&&`), `tsvector`, trigramas. |
| **GiST** | Árvore balanceada em que cada nó guarda um "resumo" que cobre os filhos (um retângulo que envolve todos os retângulos de baixo, um intervalo que envolve os intervalos). A busca desce pelos ramos cujo resumo pode conter a resposta. | Genérico: sobreposição, contenção, distância. Suporta busca do vizinho mais próximo (`ORDER BY x <-> y LIMIT k`) e `EXCLUDE`. | "Lossy": resumos podem dar falso positivo, rechecado no heap. Mais lento que GIN para "contém" em textos. | Ranges, geometria e PostGIS, `EXCLUDE`, trigramas com ordenação por similaridade. |
| **SP-GiST** | Árvores de particionamento do espaço não balanceadas: quadtrees, k-d trees, árvores de prefixo (radix). | Ótimo para dados com distribuição desigual e prefixos. | Casos de uso mais estreitos. | Endereços IP (`inet`), pontos, prefixos de texto. |
| **BRIN** | Para cada bloco de páginas (128 por padrão), guarda só um resumo, como mínimo e máximo. A busca descarta blocos cujo intervalo não pode conter o valor. | Minúsculo (KB para tabelas de TB). Manutenção quase grátis. | Só funciona se a ordem física acompanhar a coluna (logs inseridos em ordem de data). Com dados embaralhados, não descarta nada. Sempre lê blocos inteiros. | Tabelas enormes, só de inserção, com coluna correlacionada à ordem de chegada. |
| **Hash** | Tabela hash do valor. | Um pouco menor que B-tree para chaves grandes. | Só `=`; sem ordenação nem unicidade. | Raramente: igualdade em valores longos (URLs). |

```sql [brin.sql]
-- Antes de criar um BRIN, confira a correlação física (1 ou -1 = perfeita, perto de 0 = inútil)
SELECT attname, correlation FROM pg_stats WHERE tablename = 'logs' AND attname = 'criado_em';

CREATE INDEX logs_criado_brin ON logs USING brin (criado_em) WITH (pages_per_range = 32);
-- pages_per_range menor = mais preciso e um pouco maior
```

### Criar e manter em produção

```sql [producao.sql]
-- CREATE INDEX comum bloqueia INSERT/UPDATE/DELETE na tabela até terminar
CREATE INDEX CONCURRENTLY pedidos_status ON pedidos (status);
--   faz duas passadas e espera transações antigas; não pode rodar dentro de BEGIN.
--   Se falhar no meio, deixa um índice INVALID que precisa ser removido:
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
DROP INDEX CONCURRENTLY pedidos_status;

-- Índices incham com updates e deletes; reconstrua sem travar
REINDEX INDEX CONCURRENTLY pedidos_status;
```

### Por que meu índice não é usado?

- **A consulta lê boa parte da tabela.** Buscar 30% das linhas pelo índice gera leituras aleatórias; ler tudo em sequência é mais barato. O planejador está certo.
- **Função ou conversão na coluna**: `WHERE date(criado_em) = …`, `WHERE id::text = …`, `WHERE lower(email) = …` sem índice de expressão.
- **Tipos diferentes** entre parâmetro e coluna (ex.: `bigint` contra `numeric`), ou collation diferente.
- **Primeira coluna ausente** num índice composto.
- **Estatísticas desatualizadas** depois de uma carga grande: rode `ANALYZE tabela`.
- **Tabela pequena**: ler 3 páginas em sequência é mais barato que qualquer índice.
- **`OR` entre colunas diferentes**: às vezes vira um bitmap OR; às vezes compensa reescrever como `UNION ALL`.
