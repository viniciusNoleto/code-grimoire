::signature
`useEffect(setup: () => (void | cleanup), dependencias?: any[])`
::

Efeitos servem para **sincronizar o componente com algo fora do React**: conexões, timers, assinaturas, APIs do navegador, widgets de outras bibliotecas. A documentação chama efeitos de "saída de emergência": se não há sistema externo envolvido, você provavelmente não precisa de um.

| Dependências | Quando o efeito roda |
| --- | --- |
| omitidas | Depois de todo render. |
| `[]` | Uma vez após montar (e o cleanup ao desmontar). |
| `[a, b]` | Após montar e sempre que `a` ou `b` mudar por `Object.is`. |

O ciclo é sempre: **setup → (deps mudaram) cleanup → setup → … → cleanup ao desmontar**. Pense no cleanup como "desfazer o setup", não como "componentWillUnmount".

```jsx [buscar-com-race-condition.jsx]
function Perfil({ userId }) {
  const [usuario, setUsuario] = useState(null);

  useEffect(() => {
    let ignorar = false;                       // protege contra respostas fora de ordem
    fetch(`/api/usuarios/${userId}`)
      .then(r => r.json())
      .then(dados => { if (!ignorar) setUsuario(dados); });
    return () => { ignorar = true; };          // userId mudou: descarta a resposta antiga
  }, [userId]);

  // Em app real, prefira um framework ou lib de dados (TanStack Query, SWR, Server Components)
}
```

A flag `ignorar` descarta a resposta, mas a requisição continua consumindo rede. Com `AbortController`, o cleanup **cancela** a requisição de verdade:

```jsx [buscar-com-abort.jsx]
useEffect(() => {
  const controle = new AbortController();
  fetch(`/api/usuarios/${userId}`, { signal: controle.signal })
    .then(r => r.json())
    .then(setUsuario)
    .catch(e => { if (e.name !== 'AbortError') setErro(e); });   // abortar rejeita com AbortError
  return () => controle.abort();               // userId mudou ou desmontou: cancela
}, [userId]);
```

Timeouts combinados (`AbortSignal.any`, `AbortSignal.timeout`), o que `fetch` considera erro e leitura em streaming estão em [Fetch, AbortController e Streams](/web#fetch-abort-e-streams), no tomo Web.

### Você provavelmente não precisa de um efeito quando…

- **O valor pode ser calculado** a partir de props e estado: calcule no render.
- **Você quer reagir a um evento do usuário** (clique, submit): faça no handler. Um efeito não sabe *por que* o estado mudou.
- **Você quer resetar estado quando uma prop muda**: use `key` no componente.
- **Você encadeia efeitos** que setam estado que dispara outro efeito: centralize a lógica num handler ou reducer.
- **Você quer avisar o pai** de uma mudança: chame o callback do pai no mesmo handler que muda o estado.

### useLayoutEffect

::signature
`useLayoutEffect(setup, dependencias?)`
::

Mesma API, mas roda **de forma síncrona depois das mutações do DOM e antes do paint**. Use quando precisa medir o layout e ajustar algo sem o usuário ver o "pulo": posicionar tooltip, manter scroll. Bloqueia a pintura, então use com moderação. Não roda no servidor. Por que medir e escrever no DOM fora de ordem custa caro (layout forçado) está em [Renderização e animação](/web#renderizacao-e-animacao), no tomo Web.

```jsx [Tooltip.jsx]
function Tooltip({ alvoRect, children }) {
  const ref = useRef(null);
  const [altura, setAltura] = useState(0);

  useLayoutEffect(() => {
    setAltura(ref.current.getBoundingClientRect().height); // re-render acontece antes do paint
  }, []);

  const cabeEmCima = alvoRect.top - altura > 0;
  const top = cabeEmCima ? alvoRect.top - altura : alvoRect.bottom;
  return <div ref={ref} style={{ position: 'fixed', top, left: alvoRect.left }}>{children}</div>;
}
```

### useInsertionEffect

::signature
`useInsertionEffect(setup, dependencias?)`
::

Roda **antes** de o React mexer no DOM, para bibliotecas de CSS-in-JS injetarem `<style>` antes que qualquer layout effect leia o layout. Não tem acesso a refs e não pode atualizar estado. Em código de aplicação, você praticamente nunca usa.

### useEffectEvent :version[19.2]

::signature
`const onEvento = useEffectEvent(callback)`
::

Resolve um problema clássico: o efeito precisa **ler** um valor atual (tema, preferência, mudo) sem **reagir** a ele. Antes, ou o valor entrava nas dependências (reconectando à toa), ou ficava de fora (closure obsoleta e lint reclamando). O Effect Event sempre lê as props e o estado mais recentes e não entra nas dependências.

```jsx [SalaDeChat.jsx]
import { useEffect, useEffectEvent } from 'react';

function SalaDeChat({ salaId, mudo }) {
  const aoConectar = useEffectEvent((sala) => {
    if (!mudo) mostrarNotificacao(`Conectado à sala ${sala}`); // lê o "mudo" atual
  });

  useEffect(() => {
    const conexao = criarConexao(salaId);
    conexao.on('conectado', () => aoConectar(salaId));
    conexao.connect();
    return () => conexao.disconnect();
  }, [salaId]);  // trocar "mudo" não reconecta

  return <h1>Sala {salaId}</h1>;
}
```

::note{type="pitfall" title="Regras do useEffectEvent"}
Só chame de dentro de efeitos (ou de outro Effect Event) do mesmo componente: nunca durante o render, em handlers de clique ou passado para filhos. A identidade muda a cada render de propósito, então ele não vai na lista de dependências. E não use para "esconder" dependências que deveriam reexecutar o efeito.
::

### Ordem e StrictMode

Num commit: `useInsertionEffect` → mutações do DOM → `useLayoutEffect` → paint → `useEffect`. Em desenvolvimento, o StrictMode faz setup → cleanup → setup em todo efeito na montagem. Se isso quebra algo (duas conexões, evento de analytics duplicado), falta cleanup.
