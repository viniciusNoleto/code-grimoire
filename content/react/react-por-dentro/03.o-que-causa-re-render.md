Existem exatamente quatro motivos para um componente renderizar de novo:

1. **O estado dele mudou** (`useState`, `useReducer`) com um valor diferente por `Object.is`.
2. **O pai renderizou.** Por padrão, quando um componente renderiza, *todos* os filhos que ele retorna renderizam também, mudem as props ou não.
3. **Um contexto que ele lê mudou de valor** (`useContext` ou `use`).
4. **Uma store externa mudou** via `useSyncExternalStore` (Redux, Zustand e afins usam isso por baixo).

::note{type="pitfall" title="Mito comum"}
"O componente renderiza quando as props mudam." Não exatamente. Props só mudam porque o pai renderizou, e o pai renderizando já basta para o filho renderizar. Props só viram critério quando o filho está envolto em `React.memo`.
::

### React.memo, useMemo e useCallback

`React.memo(Comp)` faz o React comparar as props rasamente (`Object.is` em cada prop) e pular o render se todas forem iguais. Ele quebra fácil: um objeto, array ou função criado inline é uma referência nova a cada render do pai.

```jsx [memo.jsx]
const Linha = memo(function Linha({ item, onRemover, estilo }) { /* ... */ });

function Lista({ itens }) {
  // ❌ cada render do pai cria referências novas → memo inútil
  // <Linha estilo={{ gap: 8 }} onRemover={() => remover(id)} />

  const estilo = useMemo(() => ({ gap: 8 }), []);
  const onRemover = useCallback(id => setItens(p => p.filter(i => i.id !== id)), []);

  return itens.map(i => (
    <Linha key={i.id} item={i} estilo={estilo} onRemover={onRemover} />
  ));
}
```

- **Memoize por medição, não por reflexo.** Renders são baratos na maioria dos casos. Use o Profiler do React DevTools para achar o componente realmente lento.
- **React Compiler.** Em projetos que o adotam, o compilador insere essa memoização automaticamente em build. Vale saber que ele existe e que exige código que respeite as regras de pureza.

### Composição evita renders sem memo

Duas técnicas que resolvem a maioria dos problemas antes de recorrer a `memo`:

- **Mova o estado para baixo.** Se só um input precisa do estado, extraia o input e o estado para um componente próprio. O resto da página para de renderizar a cada tecla.
- **Passe conteúdo como `children`.** Elementos recebidos via props foram criados pelo avô. Quando o componente intermediário muda o próprio estado, esses elementos são as mesmas referências e o React os pula. A bancada acima demonstra isso na caixa tracejada.

```jsx [children.jsx]
function Rolagem({ children }) {
  const [y, setY] = useState(0);           // muda muito
  return (
    <div onScroll={e => setY(e.currentTarget.scrollTop)}>
      <Indicador y={y} />                  {/* renderiza a cada scroll */}
      {children}                           {/* NÃO renderiza: elemento veio de fora */}
    </div>
  );
}

<Rolagem><ArvorePesada /></Rolagem>
```

### Keys e identidade

Em listas, a `key` diz ao React qual item é qual entre renders. Usar o índice como key quebra quando a lista é reordenada, filtrada ou recebe itens no início: o estado interno (inputs, foco, animações) fica grudado na posição em vez do item. Use um ID estável vindo dos dados.
