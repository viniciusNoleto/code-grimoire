O JavaScript da página roda em uma única **main thread**, que também processa eventos, executa o render do React, calcula layout e pinta. Uma tarefa síncrona longa (acima de \~50 ms, o limite de "long task") congela tudo isso: cliques não respondem e animações em JS param.

Um Web Worker é outra thread com seu próprio loop de eventos. Ele **não acessa o DOM** nem o React; conversa com a página só por mensagens (`postMessage`). Os dados são copiados com o *structured clone*, que suporta objetos, arrays, Map, Set, Date, Blob e ArrayBuffer, mas não funções nem instâncias de classe com métodos. Os tipos de Worker, transferables, `SharedArrayBuffer` e `OffscreenCanvas` em profundidade estão em [Web Workers](/web#web-workers), no tomo Web.

### Criando um Worker em projeto com bundler

```ts [src/workers/csv.worker.ts]
// Roda em outra thread: sem window, sem document, sem React.
self.onmessage = (e: MessageEvent<{ id: number; payload: string }>) => {
  const { id, payload } = e.data;
  try {
    const linhas = payload.split('\n').map(l => l.split(','));
    const resumo = agregar(linhas);            // trabalho pesado
    self.postMessage({ id, result: resumo });
  } catch (err) {
    self.postMessage({ id, error: String(err) });
  }
};
```

```ts [src/hooks/useWorker.ts]
import { useCallback, useEffect, useRef } from 'react';

type Pendente = { resolve: (v: any) => void; reject: (e: Error) => void };

export function useWorker(criar: () => Worker) {
  const worker = useRef<Worker | null>(null);
  const pendentes = useRef(new Map<number, Pendente>());
  const seq = useRef(0);

  useEffect(() => {
    const w = criar();
    worker.current = w;

    w.onmessage = (e) => {
      const { id, result, error } = e.data;
      const p = pendentes.current.get(id);
      if (!p) return;
      pendentes.current.delete(id);
      error ? p.reject(new Error(error)) : p.resolve(result);
    };

    return () => {                       // cleanup: mata a thread e rejeita o que ficou
      w.terminate();
      pendentes.current.forEach(p => p.reject(new Error('worker encerrado')));
      pendentes.current.clear();
    };
  }, []); // eslint-disable-line react-hooks/exhaustive-deps

  // Promise por requisição; o id casa resposta com pedido
  return useCallback((payload: unknown, transfer: Transferable[] = []) =>
    new Promise((resolve, reject) => {
      const id = ++seq.current;
      pendentes.current.set(id, { resolve, reject });
      worker.current!.postMessage({ id, payload }, transfer);
    }), []);
}

// Uso — new URL(..., import.meta.url) funciona no Vite e no webpack 5
const processar = useWorker(() =>
  new Worker(new URL('../workers/csv.worker.ts', import.meta.url), { type: 'module' })
);
const resumo = await processar(textoDoArquivo);
```

### Detalhes que caem em entrevista

- **Transferables:** `postMessage(buffer, [buffer])` transfere a posse de um `ArrayBuffer` sem copiar. Depois disso ele fica com tamanho 0 na thread de origem. Ótimo para imagens e áudio.
- **SharedArrayBuffer** permite memória compartilhada de verdade, mas exige os headers `Cross-Origin-Opener-Policy` e `Cross-Origin-Embedder-Policy` (isolamento cross-origin).
- **Comlink** (Google) embrulha o protocolo de mensagens em chamadas de função assíncronas, eliminando o código de ids e Map acima.
- **Custo:** criar o Worker e serializar dados também gasta tempo. Para trabalho de poucos milissegundos, o Worker deixa tudo mais lento.

::note{type="note" title="Worker ou useTransition?"}
`useTransition` e `useDeferredValue` não movem trabalho para outra thread. Eles tornam o **render do React** interrompível, para que digitação continue fluida enquanto uma lista grande renderiza. Se o gargalo é renderizar muitos componentes, use transição (ou virtualização). Se é **cálculo puro** (parse, filtro de 100 mil linhas, criptografia, processamento de imagem), use Worker.
::
