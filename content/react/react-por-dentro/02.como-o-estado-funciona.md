O estado não mora na sua função. Ele fica guardado pelo React na fiber do componente, e os hooks são identificados pela **ordem de chamada**. É por isso que hooks não podem ficar dentro de `if` ou loops: a ordem precisa ser a mesma em todo render.

### Estado preso à posição na árvore

O React associa o estado à posição do componente na árvore, não à variável. Dois `<Form />` renderizados no mesmo lugar, um após o outro, compartilham o estado. Para forçar um estado novo, mude a `key`.

```jsx [reset-com-key.jsx]
// Trocar de usuário deve zerar o formulário:
<PerfilForm key={usuario.id} usuario={usuario} />

// Sem key, o React reaproveita a mesma instância
// e o estado interno do formulário "vaza" para o próximo usuário.
```

### Cada render enxerga um snapshot

Dentro de um render, `count` é uma constante. Chamar o setter não altera a variável atual, só agenda o próximo render com um valor novo.

```jsx [snapshot.jsx]
function Contador() {
  const [count, setCount] = useState(0);

  function maisTres() {
    setCount(count + 1); // 0 + 1
    setCount(count + 1); // 0 + 1
    setCount(count + 1); // 0 + 1  → resultado: 1
  }

  function maisTresCerto() {
    setCount(c => c + 1); // fila de atualizações:
    setCount(c => c + 1); // cada função recebe o
    setCount(c => c + 1); // resultado da anterior → 3
  }

  function logar() {
    setCount(count + 1);
    console.log(count); // ainda o valor antigo
  }
}
```

### Batching automático

Desde o React 18, várias atualizações dentro do mesmo tick (handlers, `setTimeout`, promises, eventos nativos) são agrupadas em **um único render**. Para forçar um render síncrono existe `flushSync`, raramente necessário. O que é um "tick", e por que tasks e microtasks rodam em ordens diferentes, está no [event loop do tomo Web](/web#event-loop).

### Bail-out com Object.is

Quando você chama o setter, o React compara o valor novo com o atual usando `Object.is`. Se for igual, ele pode pular o render. A consequência direta: **mutar um objeto e passar a mesma referência não dispara nada**.

| Comparação | Object.is | Efeito no setState |
| --- | --- | --- |
| `5` vs `5` | true | pula o render |
| `{}` vs `{}` | false | renderiza (referências diferentes) |
| `obj` mutado vs `obj` | true | pula, e a tela fica desatualizada |
| `NaN` vs `NaN` | true | pula (diferente de `===`) |
| `0` vs `-0` | false | renderiza |

```jsx [imutabilidade.jsx]
// ❌ mutação: mesma referência, React não percebe
todos.push(novo);
setTodos(todos);

// ✅ nova referência
setTodos(prev => [...prev, novo]);
setTodos(prev => prev.map(t => t.id === id ? { ...t, feito: true } : t));
setTodos(prev => prev.filter(t => t.id !== id));

// Objetos aninhados: copie cada nível que mudou
setForm(prev => ({ ...prev, endereco: { ...prev.endereco, cep } }));
```

### Estado derivado e inicialização preguiçosa

- **Não duplique estado.** Se dá para calcular a partir de props ou de outro estado, calcule no render. Sincronizar com `useEffect` causa um render extra e bugs de dessincronia.
- **Inicializador preguiçoso:** `useState(() => lerDoStorage())` roda a função só no primeiro render. `useState(lerDoStorage())` roda em todo render e descarta o resultado.
- **`useRef`** guarda um valor mutável que sobrevive entre renders e *não* causa render ao mudar. Use para IDs de timer, instâncias (Worker, EventSource) e valores lidos em callbacks.

```jsx [derivado.jsx]
// ❌ estado espelhado
const [itens, setItens] = useState([]);
const [total, setTotal] = useState(0);
useEffect(() => setTotal(itens.reduce((s, i) => s + i.preco, 0)), [itens]);

// ✅ derivado no render (useMemo só se o cálculo for caro)
const [itens, setItens] = useState([]);
const total = itens.reduce((s, i) => s + i.preco, 0);
```
