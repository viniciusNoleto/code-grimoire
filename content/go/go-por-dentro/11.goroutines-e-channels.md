Concorrência é o recurso mais famoso de Go e está na própria sintaxe: a palavra `go` dispara uma função em paralelo, e o operador `<-` manda e recebe valores entre elas. O lema da linguagem: **"não comunique compartilhando memória; compartilhe memória comunicando"**.

### Goroutine: `go f()`

```go
func main() {
	go fetch("a")          // roda em paralelo; main não espera
	go func() {            // muito comum: função anônima
		fmt.Println("em paralelo")
	}()                    // os () no fim chamam a função
	time.Sleep(time.Second) // só para o exemplo; o certo é sincronizar (abaixo)
}
```

Uma goroutine é uma função rodando de forma concorrente, gerenciada pelo **runtime do Go**, não pelo sistema operacional. Ela começa com uns poucos KB de pilha (que cresce sob demanda), e o scheduler distribui milhares ou milhões delas entre algumas threads do SO (uma por núcleo, por padrão). Criar uma goroutine por requisição, por conexão ou por item de uma fila é normal. Por isso não há `async`/`await` em Go: o código é escrito de forma síncrona e bloqueante, e quem bloqueia é só aquela goroutine.

::note{type="pitfall" title="main não espera ninguém"}
Quando `main` retorna, o programa termina e todas as goroutines morrem no meio do que estavam fazendo. Sempre sincronize: channel, `sync.WaitGroup` ou `errgroup` ([próximo capítulo](#sync-e-context)).
::

### Channel: um cano tipado

```go
ch := make(chan int)      // channel de int, sem buffer

go func() {
	ch <- 42              // ENVIA: seta apontando para dentro do channel
}()

v := <-ch                 // RECEBE: seta saindo do channel
fmt.Println(v)            // 42
```

Leia a seta como a direção do dado: `ch <- v` põe `v` no channel; `v := <-ch` tira de lá. A seta é digitada como dois caracteres, `<` e `-`; a fonte do grimório só os desenha juntos.

| Tipo | Comportamento |
| --- | --- |
| `make(chan T)` sem buffer | Envio e recebimento são um **encontro**: quem envia bloqueia até alguém receber, e vice-versa. Serve de ponto de sincronização. |
| `make(chan T, 10)` com buffer | O envio só bloqueia quando há 10 itens esperando; o recebimento, quando está vazio. É uma fila. |
| `var ch chan T` (nil) | Envio e recebimento bloqueiam **para sempre**. Útil no `select` para desligar um caso. |

### close e range

```go
func produce(n int) <-chan int {   // devolve um channel só de leitura
	out := make(chan int)
	go func() {
		defer close(out)           // avisa que não vem mais nada
		for i := range n {
			out <- i * i
		}
	}()
	return out
}

for v := range produce(5) {        // recebe até o channel ser fechado
	fmt.Println(v)                 // 0 1 4 9 16
}

v, ok := <-ch                      // ok == false: fechado e vazio
```

Regras de `close`: só quem **envia** fecha; enviar num channel fechado dá panic; receber de um fechado devolve o valor zero na hora, com `ok == false`. Não é obrigatório fechar: feche quando o lado que recebe precisa saber que acabou (para o `range` terminar).

### Direção no tipo

| Tipo | Pode |
| --- | --- |
| `chan T` | enviar e receber |
| `chan<- T` | só enviar (a seta entra no `chan`) |
| `<-chan T` | só receber (a seta sai do `chan`) |

Funções declaram a direção nos parâmetros e retornos para documentar quem faz o quê; o compilador impede o uso errado. `func worker(jobs <-chan Job, results chan<- Result)` se lê sem abrir o corpo.

### select: esperar vários channels

```go
select {
case msg := <-messages:
	fmt.Println("chegou", msg)
case err := <-errs:
	return err
case <-time.After(2 * time.Second):  // timeout
	return errors.New("demorou demais")
case <-ctx.Done():                   // cancelamento (próximo capítulo)
	return ctx.Err()
}
```

`select` espera até **um** dos casos estar pronto e executa só ele (se vários estiverem prontos, sorteia). Com `default`, não bloqueia: vira uma tentativa.

```go
select {
case queue <- job:
	// enfileirou
default:
	// fila cheia: descarta em vez de esperar
}
```

Um `for { select { ... } }` é o laço principal de muitos serviços: espera trabalho, sinais de parada e timers ao mesmo tempo.

### Timers e tickers

```go
ticker := time.NewTicker(30 * time.Second)
defer ticker.Stop()
for {
	select {
	case <-ticker.C:          // C é um channel que recebe a cada 30 s
		refresh()
	case <-ctx.Done():
		return
	}
}
```

### Deadlock e vazamento

```go
ch := make(chan int)
ch <- 1          // ninguém vai receber: bloqueia para sempre
// fatal error: all goroutines are asleep - deadlock!
```

O runtime detecta quando **todas** as goroutines estão bloqueadas e derruba o programa com essa mensagem. Pior é quando só algumas ficam presas: é um **vazamento de goroutine** (ela nunca termina, segura memória e conexões). Causa típica: uma goroutine enviando para um channel que ninguém mais vai ler porque quem lia desistiu num timeout. A saída é channel com buffer do tamanho certo ou, melhor, propagar cancelamento com `context`. Desde o Go 1.27 o perfil `goroutineleak` do `runtime/pprof` ajuda a achar esses casos.

### Quando usar channel e quando usar mutex

| Situação | Ferramenta |
| --- | --- |
| Passar dados ou posse de dados entre goroutines, pipelines, filas de trabalho | channel |
| Avisar "terminou" ou "pare" | channel fechado ou `context` |
| Proteger um estado compartilhado (um map, um contador, um cache) | `sync.Mutex` |
| Esperar N goroutines terminarem | `sync.WaitGroup` ou `errgroup` |

Os dois são idiomáticos. Um mapa protegido por mutex é mais simples que uma goroutine "dona" do mapa recebendo pedidos por channel.
