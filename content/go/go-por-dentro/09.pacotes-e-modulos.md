Dois conceitos organizam todo código Go: o **pacote** (um diretório de arquivos `.go`) e o **módulo** (o projeto inteiro, versionado, definido pelo `go.mod`).

### Pacote = diretório

Todos os arquivos `.go` de um diretório pertencem ao **mesmo pacote** e enxergam tudo uns dos outros, inclusive o que é minúsculo. Não existe import entre arquivos do mesmo pacote. O nome do pacote é, por convenção, o nome do diretório: curto, minúsculo, sem `_`, no singular (`user`, `http`, `strconv`).

```
store/
  store.go        package store
  postgres.go     package store   ← vê as funções privadas de store.go
  store_test.go   package store   (testes ficam no mesmo diretório)
```

Como o nome do pacote aparece em toda chamada, as funções não o repetem: é `http.Server`, não `http.HTTPServer`; `user.New`, não `user.NewUser`; `strings.Split`, não `strings.StringSplit`.

### Módulo e go.mod

```text [go.mod]
module github.com/ana/shop

go 1.27

require (
	github.com/jackc/pgx/v5 v5.7.4
	golang.org/x/sync v0.12.0
)

require golang.org/x/text v0.24.0 // indirect
```

| Linha | Significado |
| --- | --- |
| `module` | O caminho do módulo. É o prefixo de todos os imports internos e, se for publicado, o endereço de onde baixar. |
| `go 1.27` | Versão mínima da linguagem. Define quais recursos podem ser usados (e comportamentos como o `for` com variável nova por volta). |
| `require` | Dependências diretas com a versão exata (versionamento semântico). |
| `// indirect` | Dependência de uma dependência. |
| `replace` | Troca uma dependência por outra versão ou por um diretório local (útil para desenvolver duas coisas juntas). |
| `tool` :version[Go 1.24] | Ferramentas de desenvolvimento do projeto, rodadas com `go tool nome`. |

O `go.sum`, ao lado, guarda os hashes de cada dependência para garantir que ninguém troque o código de uma versão. Os dois arquivos vão para o git. Não existe pasta `node_modules`: as dependências ficam num cache global (`$GOPATH/pkg/mod`).

### Importar

```go
import (
	"context"                           // biblioteca padrão: sem domínio
	"fmt"

	"github.com/ana/shop/internal/order" // pacote do próprio módulo
	"github.com/jackc/pgx/v5/pgxpool"    // de terceiros

	str "strings"                        // apelido: use str.Split
	_ "github.com/jackc/pgx/v5/stdlib"   // só pelo init (registra o driver)
)
```

O que você escreve no código é o **último elemento** do caminho (ou o nome declarado no `package`): `order.Create(...)`, `pgxpool.New(...)`. Um `/v5` no fim do caminho indica a versão maior do módulo; o pacote continua se chamando `pgx`. O `goimports` (e os editores) organizam os imports em grupos: padrão primeiro, depois os outros.

::note{type="note" title="Import cíclico é erro"}
Se `order` importa `user`, `user` não pode importar `order`. O compilador recusa. A saída costuma ser mover o tipo compartilhado para um terceiro pacote ou fazer um dos lados depender de uma interface.
::

### internal: privado para o projeto

Um pacote dentro de um diretório `internal/` só pode ser importado por código que está **na árvore acima** desse `internal`. É a forma de ter pacotes que o seu projeto inteiro usa, mas que nenhum projeto de fora consegue importar.

### O layout que você vai encontrar

Não existe estrutura obrigatória, mas projetos de serviço costumam seguir algo assim:

```text
shop/
  go.mod
  go.sum
  cmd/
    api/main.go          ← cada executável em cmd/<nome>, package main
    worker/main.go
  internal/
    order/               ← regras de negócio, um pacote por assunto
      order.go
      service.go
      service_test.go
    platform/
      postgres/          ← detalhes de infraestrutura
      httpserver/
  migrations/
```

Projetos pequenos ficam com um `main.go` na raiz e alguns arquivos ao lado; está certo. Ao ler um repositório desconhecido: comece pelo `go.mod` (o que ele usa), siga para `cmd/*/main.go` (como tudo é montado) e daí para os pacotes que o `main` chama.

### Gerenciando dependências

```bash
go get github.com/google/uuid@latest   # adiciona ou atualiza
go get github.com/google/uuid@v1.6.0   # versão específica
go get -u ./...                        # atualiza tudo (menor e patch)
go mod tidy                            # remove o que não é usado, adiciona o que falta
go list -m all                         # todas as dependências e versões
go mod why github.com/x/y              # por que isso está aqui?
```

O Go escolhe a **versão mínima** que satisfaz todos os `require` (não a mais nova disponível), o que deixa builds reprodutíveis sem lockfile separado.

### Workspaces

`go work init ./api ./lib` cria um `go.work` que junta vários módulos locais para desenvolver ao mesmo tempo. Se você vir um `go.work` na raiz, é isso; normalmente ele não é commitado.
