Channels resolvem a comunicação; o pacote `sync` resolve a coordenação; e o `context` leva o cancelamento por toda a cadeia de chamadas. Juntos, cobrem quase todo código concorrente que você vai ler.

### WaitGroup: esperar várias goroutines

```go
var wg sync.WaitGroup
for _, url := range urls {
	wg.Go(func() {           // Go 1.25+: Add(1), go e Done num passo só
		fetch(url)
	})
}
wg.Wait()                    // bloqueia até todas terminarem

// forma clássica, ainda a mais comum em código existente
for _, url := range urls {
	wg.Add(1)
	go func() {
		defer wg.Done()
		fetch(url)
	}()
}
wg.Wait()
```

`wg.Go` :version[Go 1.25] já aparece em código novo; o `go fix` reescreve a forma antiga para ela.

### Mutex: proteger estado compartilhado

```go
type Counter struct {
	mu   sync.Mutex     // por convenção, logo acima dos campos que protege
	hits map[string]int
}

func (c *Counter) Inc(key string) {
	c.mu.Lock()
	defer c.mu.Unlock() // destrava em qualquer saída
	c.hits[key]++
}
```

| Tipo | Uso |
| --- | --- |
| `sync.Mutex` | Um de cada vez. `Lock` / `Unlock`. |
| `sync.RWMutex` | Vários leitores ao mesmo tempo (`RLock`/`RUnlock`) ou um escritor (`Lock`). Para muita leitura e pouca escrita. |
| `sync.Once` | `once.Do(f)` roda `f` uma única vez, mesmo com várias goroutines. Inicialização preguiçosa. |
| `sync.OnceValue(f)` | Devolve uma função que calcula `f()` uma vez e guarda o resultado. |
| `sync/atomic` | `atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]`: contadores e flags sem mutex. |
| `sync.Pool` | Reaproveitar objetos temporários (buffers) para aliviar o coletor de lixo. |

::note{type="pitfall" title="Nunca copie um mutex"}
Uma struct com `sync.Mutex` dentro precisa ser usada por ponteiro (métodos com `*T`). Copiar a struct copia o mutex, e as cópias deixam de se proteger. O `go vet` avisa ("passes lock by value").
::

### context: cancelamento e prazo

Um `context.Context` atravessa a cadeia de chamadas de uma operação (uma requisição HTTP, um job) carregando três coisas: **um sinal de cancelamento**, **um prazo** e alguns **valores** da requisição. Por convenção, é sempre o **primeiro parâmetro** e se chama `ctx`:

```go
func (s *Service) Checkout(ctx context.Context, cartID string) error {
	cart, err := s.repo.Cart(ctx, cartID)       // repassa o ctx para baixo
	if err != nil {
		return err
	}
	return s.payments.Charge(ctx, cart.Total)
}
```

```go
// as formas de criar um contexto (cada linha é uma alternativa)
ctx := context.Background()                              // raiz, no main e em testes

ctx, cancel := context.WithTimeout(ctx, 3*time.Second)   // cancela sozinho em 3 s
defer cancel()                                           // sempre: libera recursos

ctx, cancel := context.WithCancel(parent)                // cancela quando você chamar cancel()
ctx, cancel := context.WithDeadline(parent, t)           // cancela num horário
ctx = context.WithValue(parent, requestIDKey{}, "abc")   // carrega um valor
```

Cancelar um contexto cancela **todos os derivados** dele. Quando o cliente HTTP desconecta, o `r.Context()` do handler é cancelado, e com ele a consulta no banco e a chamada externa que receberam esse `ctx`.

Quem recebe um `ctx` respeita o cancelamento de dois jeitos: passando-o adiante para funções que já respeitam (banco, `http.NewRequestWithContext`) ou verificando ele mesmo:

```go
for _, item := range items {
	select {
	case <-ctx.Done():
		return ctx.Err()   // context.Canceled ou context.DeadlineExceeded
	default:
	}
	process(item)
}
```

::note{type="tip" title="O que vai no WithValue"}
Só dados da requisição que atravessam APIs (ID de requisição, usuário autenticado, trace). Nunca parâmetros opcionais de função. A chave é um tipo próprio não exportado (`type ctxKey struct{}`) para não colidir com outros pacotes.
::

### errgroup: várias tarefas, primeiro erro cancela tudo

O pacote `golang.org/x/sync/errgroup` é o `WaitGroup` com erros e contexto, e aparece em quase todo serviço:

```go
g, ctx := errgroup.WithContext(ctx)

var user *User
var orders []Order
g.Go(func() error {
	var err error
	user, err = users.Get(ctx, id)
	return err
})
g.Go(func() error {
	var err error
	orders, err = ordersRepo.List(ctx, id)
	return err
})

if err := g.Wait(); err != nil { // o primeiro erro; o ctx das outras é cancelado
	return err
}
```

`g.SetLimit(5)` limita quantas rodam ao mesmo tempo, o que transforma o errgroup num worker pool de uma linha.

### Worker pool com channels

```go
jobs := make(chan Job)
results := make(chan Result)

var wg sync.WaitGroup
for range 4 {                     // 4 workers
	wg.Go(func() {
		for j := range jobs {     // cada worker consome até jobs fechar
			results <- handle(j)
		}
	})
}

go func() {                       // fecha results quando todos os workers terminarem
	wg.Wait()
	close(results)
}()

go func() {
	defer close(jobs)
	for _, j := range all {
		jobs <- j
	}
}()

for r := range results {
	fmt.Println(r)
}
```

É o padrão "fan-out, fan-in": um produtor, N workers, um consumidor. Quando você vir três goroutines e dois channels assim, é isso.

### Detector de corridas

```bash
go test -race ./...
go run -race .
```

Uma **data race** é duas goroutines acessando a mesma variável ao mesmo tempo, com pelo menos uma escrevendo, sem sincronização. O resultado é imprevisível. O `-race` instrumenta o binário e relata cada corrida com os dois stack traces. Rode os testes com ele no CI.

### Testes de código concorrente

O pacote `testing/synctest` :version[Go 1.25] roda o teste numa "bolha" com relógio falso: `time.Sleep(time.Hour)` lá dentro termina na hora, e `synctest.Wait()` espera todas as goroutines da bolha ficarem bloqueadas. Torna testáveis timeouts e retries sem testes lentos ou instáveis.
