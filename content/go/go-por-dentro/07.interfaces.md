Uma interface é uma lista de métodos. Qualquer tipo que tenha esses métodos **satisfaz** a interface automaticamente, sem escrever `implements`. Esse detalhe muda a forma de organizar código: quem usa define a interface de que precisa, e os tipos se encaixam sem saber disso.

### Satisfação implícita

```go
type Shape interface {
	Area() float64
	Perimeter() float64
}

type Rect struct{ W, H float64 }
func (r Rect) Area() float64      { return r.W * r.H }
func (r Rect) Perimeter() float64 { return 2 * (r.W + r.H) }

type Circle struct{ R float64 }
func (c Circle) Area() float64      { return math.Pi * c.R * c.R }
func (c Circle) Perimeter() float64 { return 2 * math.Pi * c.R }

func describe(s Shape) {          // aceita qualquer coisa com Area e Perimeter
	fmt.Printf("área %.2f\n", s.Area())
}

describe(Rect{2, 3})
describe(Circle{1})
shapes := []Shape{Rect{1, 1}, Circle{2}}
```

`Rect` nunca menciona `Shape`. Ele satisfaz porque tem os dois métodos. Para garantir isso em tempo de compilação (e documentar a intenção), você vai ver:

```go
var _ Shape = Rect{}          // não compila se Rect deixar de satisfazer Shape
var _ Shape = (*Server)(nil)  // versão para quando os métodos têm receptor ponteiro
```

::note{type="pitfall" title="Receptor ponteiro e interfaces"}
Se o método foi declarado em `*T`, só `*T` satisfaz a interface, não `T`. Com `func (s *Server) Serve()`, `var h Handler = Server{}` não compila; `&Server{}` compila. O erro diz "method has pointer receiver".
::

### Interfaces pequenas: o estilo Go

As interfaces mais importantes da biblioteca padrão têm **um método só**, e o nome termina em `-er`:

| Interface | Método | Quem satisfaz |
| --- | --- | --- |
| `io.Reader` | `Read(p []byte) (n int, err error)` | arquivos, conexões, corpo HTTP, `strings.Reader`, `bytes.Buffer`, gzip… |
| `io.Writer` | `Write(p []byte) (n int, err error)` | arquivos, `os.Stdout`, resposta HTTP, `bytes.Buffer`, hashes… |
| `io.Closer` | `Close() error` | tudo que precisa ser liberado |
| `fmt.Stringer` | `String() string` | qualquer tipo que queira controlar como é impresso |
| `error` | `Error() string` | todo erro ([próximo capítulo](#erros)) |
| `http.Handler` | `ServeHTTP(w, r)` | todo handler HTTP |
| `sort.Interface` | `Len`, `Less`, `Swap` | coleções ordenáveis (código antigo; hoje `slices.SortFunc`) |

Por isso dá para encadear quase tudo: `io.Copy(dst Writer, src Reader)` copia de um arquivo para a rede, da rede para um gzip, de um gzip para um hash, sem que nenhum desses tipos conheça os outros. Interfaces maiores são compostas das pequenas:

```go
type ReadWriter interface {
	Reader      // embutir interface = incluir os métodos dela
	Writer
}
```

### any: a interface vazia

`interface{}` não exige nenhum método, então **todo tipo** a satisfaz. Desde o Go 1.18 ela tem o apelido `any`. Aparece onde o tipo realmente varia: `fmt.Println(a ...any)`, JSON genérico (`map[string]any`), contextos. Em código antigo você verá `interface{}`; é a mesma coisa.

Uma variável `any` esconde o tipo concreto. Para usar o valor, é preciso recuperá-lo.

### Type assertion: `x.(T)`

```go
var v any = "olá"

s := v.(string)          // "olá"; se v não for string: PANIC
n, ok := v.(int)         // vírgula-ok: n == 0, ok == false, sem panic

if w, ok := out.(io.WriterTo); ok { // "este valor TAMBÉM sabe fazer X?"
	w.WriteTo(dst)
}
```

O segundo uso é muito comum na biblioteca padrão: receber uma interface pequena e testar se o valor tem uma capacidade extra, para usar um caminho mais rápido.

### Type switch

```go
func kind(v any) string {
	switch x := v.(type) {   // .(type) só existe dentro de switch
	case nil:
		return "nil"
	case int, int64:
		return fmt.Sprint("inteiro ", x) // com dois tipos no case, x continua any
	case string:
		return "texto de " + strconv.Itoa(len(x)) + " bytes" // x é string aqui
	case error:
		return "erro: " + x.Error()
	case fmt.Stringer:
		return x.String()
	default:
		return fmt.Sprintf("outro: %T", x)          // %T imprime o tipo
	}
}
```

### Por dentro: tipo + valor

Um valor de interface guarda dois ponteiros: o **tipo concreto** e o **valor**. Ele só é `nil` quando os dois são `nil`. Daí a armadilha mais famosa da linguagem:

```go
type MyErr struct{}
func (*MyErr) Error() string { return "falhou" }

func check() error {
	var p *MyErr = nil
	return p                  // a interface error recebe (tipo=*MyErr, valor=nil)
}

err := check()
fmt.Println(err == nil)       // false! o tipo está preenchido
```

::note{type="pitfall" title="Devolva nil literal"}
Uma função que devolve `error` deve escrever `return nil` no caminho de sucesso, nunca devolver uma variável de tipo concreto que por acaso é `nil`. O mesmo vale para qualquer interface.
::

### Onde declarar a interface

Em Java e C#, a interface fica junto da implementação. Em Go, o costume é o contrário: **quem consome declara a interface**, só com os métodos que usa.

```go
// pacote notification: só precisa enviar, então pede só isso
type Sender interface {
	Send(ctx context.Context, to, body string) error
}

type Service struct{ sender Sender }
```

O pacote de e-mail exporta um tipo concreto (`*smtp.Client`, `*SESClient`) e não precisa conhecer `Sender`. Nos testes, um fake de uma linha satisfaz a interface. O provérbio da comunidade resume: **"aceite interfaces, devolva structs"**. Ao ler código Go, uma interface declarada no mesmo arquivo de quem a usa é exatamente isso, não duplicação.
