Go não tem exceções. Uma função que pode falhar devolve um `error` como **último valor de retorno**, e quem chama decide o que fazer ali mesmo. É verboso, mas o caminho do erro fica sempre visível: lendo a função, você vê cada ponto que pode falhar.

### A interface error

```go
type error interface {
	Error() string
}
```

Qualquer tipo com um método `Error() string` é um erro. `nil` significa "deu certo".

### O padrão que aparece em todo lugar

```go
func loadUser(path string) (*User, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return nil, fmt.Errorf("ler %s: %w", path, err)
	}

	var u User
	if err := json.Unmarshal(data, &u); err != nil {
		return nil, fmt.Errorf("decodificar usuário: %w", err)
	}
	return &u, nil
}
```

Três regras de leitura:

1. **O erro vem por último**, e quando há erro os outros retornos são valores zero (`nil`, `0`, `""`) que não devem ser usados.
2. **Trate logo depois da chamada**, com `if err != nil`. O caminho feliz segue sem indentação.
3. **Ou trate, ou devolva com contexto.** Não faça os dois (logar e devolver gera o mesmo erro logado várias vezes).

### Criando erros

```go
errors.New("saldo insuficiente")                     // texto fixo
fmt.Errorf("pedido %d: saldo insuficiente", id)      // texto formatado
fmt.Errorf("salvar pedido %d: %w", id, err)          // EMBRULHA err
```

Mensagens de erro em Go começam com **minúscula** e não terminam com ponto, porque são concatenadas: o resultado final fica como `salvar pedido 7: ler config.json: open config.json: no such file or directory`, uma trilha de onde a falha veio.

### Embrulhar: `%w` e a cadeia de erros

O verbo `%w` do `fmt.Errorf` guarda o erro original dentro do novo. Isso forma uma cadeia que pode ser inspecionada sem comparar textos:

| Função | Pergunta | Exemplo |
| --- | --- | --- |
| `errors.Is(err, alvo)` | "algum erro da cadeia **é** este valor?" | `errors.Is(err, os.ErrNotExist)` |
| `errors.As(err, &alvo)` | "algum erro da cadeia **é deste tipo**? Se sim, me dê" | `var pe *fs.PathError; errors.As(err, &pe)` |
| `errors.AsType[T](err)` :version[Go 1.26] | o mesmo que `As`, com generics | `pe, ok := errors.AsType[*fs.PathError](err)` |
| `errors.Unwrap(err)` | o erro de dentro (um nível) | raro no dia a dia |

```go
user, err := loadUser("ana.json")
if errors.Is(err, os.ErrNotExist) {      // funciona mesmo embrulhado duas vezes
	user = defaultUser()
} else if err != nil {
	return err
}
```

::note{type="pitfall" title="Nunca compare com == nem com o texto"}
`err == os.ErrNotExist` falha assim que alguém embrulha o erro, e `strings.Contains(err.Error(), "not found")` quebra quando a mensagem muda. Use `errors.Is` e `errors.As`. Com `%v` no lugar de `%w`, o texto é incluído mas a cadeia é cortada: use `%v` de propósito quando não quiser expor o erro interno.
::

### Erros sentinela

Erros fixos exportados por um pacote, para quem chama poder testar com `errors.Is`. Por convenção, o nome começa com `Err`:

```go
var (
	ErrNotFound     = errors.New("não encontrado")
	ErrInsufficient = errors.New("saldo insuficiente")
)

func (r *Repo) Find(id int64) (*User, error) {
	// ...
	if errors.Is(err, sql.ErrNoRows) {
		return nil, ErrNotFound      // traduz o erro do banco para o do domínio
	}
}
```

Exemplos da biblioteca padrão: `io.EOF` (fim da leitura, não é falha de verdade), `sql.ErrNoRows`, `os.ErrNotExist`, `context.Canceled`, `http.ErrServerClosed`.

### Tipos de erro próprios

Quando o erro precisa carregar dados (campo inválido, código HTTP), crie um tipo:

```go
type ValidationError struct {
	Field string
	Msg   string
}

func (e *ValidationError) Error() string {
	return e.Field + ": " + e.Msg
}

func validate(u User) error {
	if u.Email == "" {
		return &ValidationError{Field: "email", Msg: "obrigatório"}
	}
	return nil
}

// quem chama
if ve, ok := errors.AsType[*ValidationError](err); ok {
	respond(w, 422, ve.Field)
}

// forma antiga, equivalente
var ve *ValidationError
if errors.As(err, &ve) {
	respond(w, 422, ve.Field)
}
```

### Vários erros de uma vez

```go
var errs []error
for _, f := range files {
	if err := process(f); err != nil {
		errs = append(errs, err)
	}
}
return errors.Join(errs...)   // nil se a lista estiver vazia; Is/As enxergam todos
```

### Quando o erro é ignorado

`_ = f.Close()` e chamadas como `fmt.Println(...)` sem checar o retorno são ignorados conscientes. Ignorar sem `_` em algo importante é bug; linters como `errcheck` (no `golangci-lint`) apontam isso.

### Lendo o volume de `if err != nil`

Num arquivo Go típico, um terço das linhas é tratamento de erro. Ao ler, você aprende a "pular" esses blocos: leia a chamada, dê uma olhada no texto do `fmt.Errorf` (ele conta o que a linha faz) e siga. O que merece atenção é o bloco de erro que **não** devolve: ali alguém decidiu tratar, tentar de novo ou ignorar.
